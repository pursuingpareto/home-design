## 1. Objective and user-visible behavior

Give every revision real artifact statuses and payloads instead of `MISSING`:

- derive artifacts after each commit;
- store them;
- compute their status from fingerprints (artifacts.md §2.1);
- serve the manifest and individual artifacts through the service layer.

Artifact *content* comes from derivation functions registered by `GEOM-001` and `EST-001`. This task builds everything around them, and tests it with stub derivations. There is no HTTP yet.

## 3. Scope

**In scope**

- **Derivation registry:** each artifact type registers `generator_id`, `generator_version`, `inputs(snapshot, context) -> dict` (the fingerprinted input object), and `derive(inputs, context) -> Outcome`. An outcome is `CURRENT` plus a payload, `UNAVAILABLE` plus an optional payload, or `FAILED` plus an error.
- **Envelope builder:** artifacts.md §2. `suitability` is always `preliminary`, `claims.*` are always `false`, and `PRELIMINARY_UNVERIFIED` is always present (AC-08).
- **Storage:** an `artifacts` table and its store methods, for both the in-memory and PostgreSQL stores (§5).
- **Execution:** derive-after-commit with lazy recompute on read (§4).
- **Service calls:** `artifact_manifest(project_id, revision_id | None)` and `get_artifact(project_id, artifact_type, revision_id | None)`. Commit and create responses report real `artifact_statuses`.

**Non-goals**

- The four payloads → `GEOM-001` (`plan2d`, `mesh3d`) and `EST-001` (`timber_schedule`, `preliminary_estimate`).
- Background workers, queues, and the transactional outbox (§4, deferred).
- HTTP status mapping (202, 404, 503) → API task; this task returns typed results that map one-to-one.

## 4. Execution model (approved — §8 item 1)

1. **After a commit:** once the commit transaction has committed, the service derives every registered artifact for the new revision in dependency order (the estimate after the schedule). Each result is stored in its own transaction.
   - A derivation that raises is stored as `FAILED` with an error code. The committed revision is never affected (dependencies.md §6).
   - The commit response reports the resulting statuses.
2. **Lazy recompute on read:** when an artifact is requested and no stored row matches the current expected fingerprint, the artifact is derived then, stored, and returned. The manifest only reports `MISSING` or `STALE` and never derives (§6). *(Wording corrected during implementation; the draft also said "the manifest".)* This covers a crash between commit and derivation, a generator version bump, and a price-book change. No outbox is needed.
3. **Statuses VS-01 never produces:** `QUEUED`, `COMPUTING`, and `SUPERSEDED`, because derivation is synchronous. They stay in the contract for a later asynchronous worker. Adding that worker (and the outbox) is a later task, needed only when derivations become slow.

**Why:** every VS-01 derivation is a pure function of a few kilobytes of snapshot and takes milliseconds. Workers would add moving parts without any user-visible benefit.

## 5. Storage (approved — §8 item 2)

```text
artifacts (project_id uuid, revision_id uuid, artifact_type text, input_fingerprint text,
           generator_id text, generator_version text, status text CHECK (status IN ('CURRENT','UNAVAILABLE','FAILED')),
           payload jsonb NULL, error jsonb NULL, warnings jsonb, generated_at timestamptz,
           PRIMARY KEY (revision_id, artifact_type, input_fingerprint))
```

- **Derived data:** artifacts may be recomputed or deleted at any time. Unlike revisions, they are not immutable, and the append-only triggers do not apply to this table.
- **Idempotent writes:** writing the same key twice keeps the first row. Results are deterministic, so concurrent derivations of the same input are harmless.

## 6. Status rules

For a requested revision R and artifact type T, the service computes T's expected fingerprint from R's snapshot, plus any external inputs (the price book, in `EST-001`). Then:

| Condition | Status reported |
|---|---|
| A stored row for (R, T, expected fingerprint) exists | that row's status: `CURRENT`, `UNAVAILABLE`, or `FAILED` |
| Rows for (R, T) exist, but none has the expected fingerprint | `STALE` in the manifest, then recomputed on `get_artifact` |
| No row for (R, T) | `MISSING` in the manifest, then computed on `get_artifact` |

- **Serving rules:** a payload is served only with `CURRENT` (or `UNAVAILABLE` with its partial payload, artifacts.md §8.1). A stale or failed payload is never labeled `CURRENT`.
- **Historical revisions:** an artifact requested for an explicit historical revision is served as current *for that revision* and is flagged `"head": false` (artifacts.md §4).

## 7. Acceptance criteria and automated tests

These use stub derivations and run against both stores.

1. **Every revision has artifacts:** after create and after each commit, the manifest lists exactly the four artifact types (artifacts.md §10, test 1) with stored statuses, and the commit response's `artifact_statuses` match it.
2. **Envelopes:** every envelope has `suitability: "preliminary"`, all `claims` false, and `PRELIMINARY_UNVERIFIED` (test 7). The fingerprint equals SHA-256 of the canonical input object.
3. **Freshness:** after a new commit, the old head's artifacts are never served as `CURRENT` for the new head, and the new fingerprints differ (test 5).
4. **Failure isolation:** a stub derivation that raises yields `FAILED` with an error. The revision is committed and readable, and the other artifacts are unaffected.
5. **Lazy recompute:** deleting stored artifacts (simulating a crash) leads to `MISSING` in the manifest; `get_artifact` then computes, stores, and returns `CURRENT`.
6. **Version bump:** bumping a stub's `generator_version` gives `STALE` in the manifest, then a recomputed `CURRENT`.
7. **Historical requests:** an older revision's artifact is served with `head: false`, and is never labeled as the live head.
8. **Determinism:** identical revisions give identical payloads and fingerprints, and repeated derivation stores one row.

- `docs/architecture/schemas/artifacts.v1.schema.json` is exported and drift-checked.

**Tests:** 323 pytest tests pass, 28 of them new, covering all §7 criteria on both stores with stub derivations:
- stored statuses on create and commit;
- the envelope contract and the recomputed fingerprint;
- old heads never `CURRENT` for a new head;
- failure isolation, including no leaked internals;
- `UPSTREAM_NOT_CURRENT` for dependents, and non-I-JSON payloads as failures;
- lazy derivation after deleted rows, including dependencies;
- a generator version bump making artifacts `STALE`;
- an external-input change making only the estimate `STALE`;
- historical `head: false`;
- re-derivation keeping one row;
- unregistered types as `MISSING`, unknown types, revisions, and projects, and no-op statuses.

**Choices made during implementation:**

- **External inputs:** `Derivation.external_inputs(tx, project_id)` returns inputs from outside the snapshot, such as the EST-001 price book. They are merged into the fingerprint input object and passed to the derivation, so changing them makes exactly that artifact `STALE`.
- **Dependents:** a dependent derivation runs only when every declared dependency is `CURRENT`. Otherwise it is stored `FAILED` with `UPSTREAM_NOT_CURRENT`. Lazy derivation of a dependent first derives its dependencies. Both error codes are documented in artifacts.md §2.1.
- **Context-only external keys (added by EST-001):** keys returned by `external_inputs` that start with `_` reach the derivation but are not fingerprinted. They must be fully determined by the fingerprinted keys; for example, a price book's rows are determined by its append-only version.
- **Payload check:** payloads are checked for I-JSON (RFC 8785 canonicalizable) before storage. A payload with NaN or infinity is a `DERIVATION_FAILED` artifact, never a stored or served payload.
- **Import order:** `ProjectService` imports `ArtifactService` lazily, because the two packages import each other's modules.

**Limitations:**

- No payloads exist yet (GEOM-001, EST-001). Production statuses are `MISSING` until those register.
- Derivation is synchronous, and there is no outbox (dependencies.md §6).
- `generated_at` is the commit or read time passed in; the services read no clock.
