**Status:** Done (2026-11-19) — see §13 for implementation notes  
**Owner module:** `frontend/` (new): presentation only, over the API-001 HTTP API  
**Slice:** VS-01

## 1. Objective and user-visible behavior

Deliver the browser application that VS-01's goal names. A user can:

- sign in with a development token (D050);
- create Reference House 001 and reopen it later;
- see the 2D plan and the 3D frame side by side, derived from one revision;
- edit the footprint width and depth with an impact preview and confirmation;
- read the timber schedule and the estimate status;
- enter unit prices in a price-book form and see the preliminary estimate;
- browse revision history, view an older revision read-only, and undo to it.

Framing and estimates are labeled preliminary throughout. The client holds no building rules: it sends typed commands, shows server results, and renders derived artifacts exactly as served (D028, interfaces.md §6).

## 3. Scope

**In scope**

- A `frontend/` application: build tooling, the generated API client, and the screens in §4.
- 2D plan rendering from `plan2d`, and 3D rendering from `mesh3d`, behind a renderer interface (§6).
- Unit display and input in imperial or metric (§7).
- A small backend addition, `GET /api/v1/projects` (proposal 8, §8.1).
- Unit tests, component tests, and browser end-to-end tests against a real API server (§9).

**Non-goals**

- Editing by dragging in 2D or 3D. VS-01 edits footprint dimensions through numeric fields; direct manipulation comes later (FR-03).
- Commands other than `SetFootprintDimensions` and `UndoToRevision` (proposal 3). Story heights, roof, grid, and sections follow in `UI-002`.
- Production authentication, accounts, sharing (open question 8, FR-11).
- AI interaction, alternatives, drawings and exports (glTF, DXF, IFC: artifacts.md §11).
- Offline support, mobile layouts beyond a usable narrow view, internationalization.

## 4. Screens (proposal 3)

| Screen | Contents |
|---|---|
| **Sign in** | Enter a development token; it is checked against the API before use (§8, proposal 7) |
| **Projects** | The caller's projects (newest first) and "Create Reference House 001" (proposal 8) |
| **Workspace** | A revision bar, the 2D plan and 3D view side by side, an edit panel, the schedule and estimate, and history (below) |

**Workspace details:**

- **Revision bar:** revision sequence and short ID, a **head** or **historical** label, and one status chip per artifact (`CURRENT`, `STALE`, `MISSING`, `UNAVAILABLE`, `FAILED`).
- **Preliminary banner:** always visible, with the `PRELIMINARY_UNVERIFIED` message from the envelope, never hard-coded text (AC-08).
- **2D plan:**
  - posts and beams per plane (level 0, level 1, eave), with a plane selector;
  - the footprint outline;
  - the roof ridge and eave outline;
  - the two dimension strings, labeled from `dimensions[].value_m`, never measured from pixels (FR-03).
- **3D view:** orbit, pan, and zoom, with the members as oriented boxes, the roof surfaces, and level outlines.
- **Selection:** selecting a member in the plan, the 3D view, or the schedule highlights it in the other two, matched by `member_id`.
- **Edit panel:** width and depth in display units → **Preview** → an impact dialog → **Confirm**. See §5.
- **Schedule:**
  - the member rows (generation key, role, nominal section, species, length, quantity);
  - the aggregates;
  - the `assumptions` messages;
  - the units.
- **Estimate:**
  - `UNAVAILABLE`: "Costs not configured" with the gating warnings, never a zero total (artifacts.md §8.1);
  - otherwise: coverage, totals in the book's currency, unpriced lines, and the price book's source and date.
- **Price book:** a form opened from the estimate panel. See §5.1.
- **History:**
  - revisions in sequence order, with the command type;
  - opening one shows its artifacts read-only, labeled historical (`head: false`, artifacts.md §4);
  - "Undo to this revision" runs `UndoToRevision` through the same preview flow.

## 5. Edit flow and errors (proposal 4)

1. **Command:** the client builds `SetFootprintDimensions` with a fresh `command_id`, the head `revision_id` as base, and both dimensions converted to meters (§7).
2. **Preview:** the impact dialog shows the server's preview, translated only for display:
   - classification;
   - field changes, before → after in display units;
   - counts of members added, removed, and updated;
   - impacted artifacts and warnings.
3. **No-op:** when `is_noop` is true, the dialog says nothing will change and offers no confirmation (D045).
4. **Confirm:** sends the same command with `preview_token`. If the request fails in transit, the client retries the **same** `command_id`, so an earlier success comes back as `replayed` instead of a duplicate (interfaces.md §4).
5. **After commit:** the workspace moves to the new head and loads its artifacts. Until both views are paired (§6), it shows "Updating…" instead of the previous geometry.

**Error handling:**

| Error | Client behavior |
|---|---|
| 422 with details | Show the envelope `message`. Attach each detail to the input whose `args.*` path appears in `path` or `related_paths` (D037); otherwise show it in the dialog. The server's validation is not duplicated |
| `REVISION_CONFLICT` | Someone (or another tab) moved the head. Reload the head, keep the user's inputs, and ask for a fresh preview |
| `PREVIEW_EXPIRED`, `PREVIEW_INVALID` | Discard the token, preview again, and ask for confirmation again. Never confirm silently |
| `PREVIEW_REQUIRED` | A client bug for these commands; report it as an unexpected error |
| 401 | Return to sign in |
| 404 on a project route | "Project not found" (D050: it may belong to someone else) |
| 500 or network failure | A generic error with the `request_id`, so it can be found in server logs |

### 5.1 Price-book form (proposal 3, as amended)

Setting a price book is not a model command: it creates no revision and needs no preview (artifacts.md §8.2). The form is a plain edit-and-save.

- **Rows:** one row per line item `key` in the head's estimate. The estimate lists its line items even when `UNAVAILABLE`, so the form never invents keys. Each row shows role, nominal section, and the quantity.
- **Existing book:** values are loaded from `GET …/price-book`. Rows of the current book whose key matches no line item are kept and shown as unused, matching the server's `PRICE_ROWS_UNUSED` warning, so saving never drops them silently.
- **Book fields:**
  - `source` and `geography`: required text;
  - `as_of`: a date;
  - `currency`: shown as USD and not editable (VS-01 accepts only `USD`).
- **Prices:**
  - Prices are entered per linear foot in imperial mode, or per meter in metric. They are parsed as decimal strings with at most two decimal places, never through floating point.
  - A blank price leaves the row out, which gives partial coverage. A partial estimate never shows a grand total (artifacts.md §8.1).
  - **Stored per meter:** the book's unit is the meter, in whole cents. A per-foot price is converted exactly (cents per ft × 1250 / 381) and rounded half-even to whole cents per meter. The form shows the stored per-meter price next to each row before saving, so the user sees the value the server will keep.
  - **Reloading in imperial mode:** a stored price converts back to a per-foot price that is usually not a whole cent. For example, $10.00/ft is stored as $32.81/m, which is $10.0005/ft. The form shows the stored per-meter price as authoritative, with the per-foot equivalent labeled approximate.
- **Save:**
  - `PUT …/price-book` creates a new book version (append-only, artifacts.md §8.2).
  - The workspace then shows the estimate as `STALE` until it is re-read as `CURRENT`, with its coverage, totals, and the book's source, date, and version.
  - There is no "clear" action, because VS-01 does not support clearing a book.
- **Errors:** 422 details are attached to fields by path (`rows[k].unit_price_minor`, `source`, `as_of`), and the rest are shown above the form.
- **Concurrent edits:** `PUT` is not conditional. If the saved version is not the loaded version + 1, the form says another change was saved in between, and shows the current book.

## 6. Views and consistency (proposal 5)

- **Pairing rule** (artifacts.md §4, §10 test 6): a pure function `pairViews(plan, mesh)` returns either a renderable pair or the reason it cannot pair:
  - **renderable** only when both envelopes are `CURRENT` and share `source_revision_id`;
  - otherwise each view shows its status, and neither shows older geometry.
  
  The workspace renders only through this function.
- **Revision identity:** every rendered view and the schedule show the revision they came from (AC-07). A historical revision is never labeled as the head.
- **Renderer boundary:** `Plan2dView` (SVG) and `Mesh3dView` (Three.js) take a payload and selection, and report selections back. Neither reads the API or the semantic snapshot, so either renderer can be replaced (AGENTS.md principle 5; open question 3).
- **Coordinates:** payloads are meters with +Z up (D026). The 3D view sets the camera's up vector to +Z instead of rotating the data. The plan draws +Y north, up on screen.
- **No geometry is computed in the client** beyond tessellating the documented primitives (oriented boxes, roof rings).

## 7. Units (proposal 6)

- **Display:** imperial feet-inches by default (Reference House 001 is specified in feet, D025), with a metric toggle remembered per browser.
  - Lengths display to 1/16 inch, or to the millimeter in metric.
  - Pitch displays as rise per 12 (for example 9/12) next to degrees.
  - Display rounding never feeds back into a command.
- **Input:** accepts `36'`, `36' 6"`, `36' 6 1/2"`, `438.5"`, `36 ft 6 in`, and metric `10.9728 m` or `10972.8 mm`, with any field in either system.
- **Exact conversion:** naive `36 × 0.3048` in IEEE doubles is `10.972800000000001`, not `10.9728`. Re-entering the current width would then produce a real (sub-micrometer) change instead of a no-op. The client therefore:
  - parses imperial input to an integer number of 1/64-inch steps `n` (finer input is rejected);
  - converts with `n × 396875 / 1e9`: the product is an exact integer, so the result is the double nearest the exact decimal length (1/64 in = 0.000396875 m exactly);
  - parses metric input as a decimal string.

  Re-entering 36' then yields exactly the stored `10.9728`, and a no-op.
- **Tests** cover the D025 dimensions, round trips, fractions, rejection of malformed input, and the no-op case end to end.

## 8. Technology and project layout (proposals 1, 2, 7)

```
frontend/
  package.json, package-lock.json, tsconfig.json, vite.config.ts
  src/api/schema.d.ts        generated from docs/architecture/schemas/openapi.v1.json (committed)
  src/api/client.ts          typed client, bearer token, error envelope → typed errors
  src/units/                 parsing, formatting, exact conversion
  src/views/                 pairViews, Plan2dView (SVG), Mesh3dView (Three.js)
  src/workspace/, src/projects/, src/auth/
  tests/                     Vitest unit and component tests
  e2e/                       Playwright tests against a real API server
```

- **Development server:** Vite proxies `/api` to a local uvicorn, so the browser makes same-origin requests and needs no CORS. `HOMEDESIGN_CORS_ORIGINS` remains for other setups.
- **Token handling:** the token is held in `sessionStorage` (cleared with the tab), sent only as `Authorization: Bearer`, and never logged or put in a URL.

### 8.1 Listing projects (proposal 8, option a)

`GET /api/v1/projects` returns the caller's projects:

```json
{"projects": [{"project_id": "…", "head_revision_id": "…", "head_sequence": 2, "created_at": "2026-11-19T12:00:00.000000Z"}]}
```

- **Only the caller's projects:** those whose `created_by` is the authenticated actor (D050). Other actors' projects are never listed. No token is 401.
- **Order:** newest first by `created_at`, then by `project_id`, so the order is deterministic.
- **No paging in VS-01**, because owners have few projects. Paging is added before the list can grow large.
- **Backend work:**
  - `ProjectService.list_projects(actor_id)`, with a store method for both stores;
  - a migration adding an index on `projects (created_by, created_at)`;
  - the route and its response model, regenerated into `openapi.v1.json`;
  - API tests for ownership, order, an empty list, and 401.

   - the price-book form builds the expected book for blank, partial, and complete prices, including the per-foot conversion and half-even rounding.

   The fixtures are regenerated by a backend script and drift-checked like the schemas.
5. **End to end** (Playwright, against uvicorn with the in-memory store and a test token):
   - **AC-01:** create Reference House 001; 2D shows 36' × 24' and the 3D bounding box of the footprint matches.
   - **AC-02 and AC-07:** preview and confirm width 40'. Both views show the new revision and 40', and the schedule shows the new lengths. At no point is old geometry shown under the new revision label.
   - **AC-05:** reload the page and reopen the project from the list: same revision ID and dimensions.
   - **AC-06:** width 100' gives a field-level error and no new revision.
   - **AC-08:** the banner is visible in the workspace and on historical revisions.
   - **Price book:** price both line items. The estimate becomes `CURRENT` with `complete` coverage and a total equal to the sum of the line amounts. Then clear one price: `partial`, with no grand total.
   - **Undo:** undo to revision 1 through the preview flow, then check that history shows three revisions.
   - **Conflict:** a commit from a second tab produces the conflict message and a fresh preview.
6. **Project list** (backend, §8.1): API tests on both stores for ownership, order, the empty list, and 401, with responses validated against the committed OpenAPI.
7. **Accessibility baseline:** every control has a label and is reachable by keyboard; the 2D plan has a text alternative listing its dimensions.

## 10. Implementation guidance (not prescriptive)

- Keep server data in one place per revision, keyed by `(project_id, revision_id)`. Artifacts of a revision never change, so they can be cached for the session.
- Build Three.js geometry once per payload and dispose of it when the revision changes.
- Running locally: `npm run dev` (frontend) and uvicorn (backend README), documented in `frontend/README.md`.

## 13. Implementation notes (2026-11-19)

**Delivered:**
- **Backend:** `GET /api/v1/projects` (§8.1), with `ProjectService.list_projects`, `list_projects` on both stores, and migration `0004_projects_by_owner.sql`.
- **OpenAPI:** the four artifact payloads are now named components (`Plan2dPayload`, `Mesh3dPayload`, `TimberSchedulePayload`, `PreliminaryEstimatePayload`), so the client's payload types are generated, not hand-written.
- **Fixtures:** `homedesign.api.ui_fixtures` captures Reference House 001 envelopes, a preview, and a price book from the real services into `frontend/tests/fixtures/`. A backend test fails when the file is stale.
- **`frontend/`:** Vite, React 18, and strict TypeScript, with:
  - the generated client (`src/api/schema.d.ts`, `check:api`);
  - exact units and money (`src/units/`);
  - `pairViews`, `Plan2dView` (SVG), and `Mesh3dView` (Three.js);
  - the workspace: revision bar, preliminary banner, edit panel with impact dialog, schedule, estimate, price-book form, and history with undo;
  - sign-in and the project list.
- **Development launch:** `.claude/launch.json` starts an in-memory API and the dev server.

**Tests:**
- **Backend:** 439 pytest tests pass, including project-list ownership and order, and fixture drift.
- **Frontend:** 34 Vitest tests:
  - units, money, and half-even rounding;
  - every status combination for `pairViews`;
  - mesh tessellation: 58 boxes with the schedule's and plan's IDs, and post and beam orientation;
  - components;
  - the workspace driven through the real client over an in-memory HTTP fake.
- **End to end:** 8 Playwright tests in Chromium against uvicorn and Vite:
  - AC-01;
  - AC-02 and AC-07, with a DOM observer asserting that the paired views never show a revision other than the revision bar's;
  - AC-05, AC-06, AC-08 and undo;
  - a conflict between two tabs;
  - complete then partial price books;
  - unknown tokens, and other actors.
- **Also checked:** `tsc --noEmit`, `npm run build`, `check:api`, `schema_export --check`, and a manual look in a browser.

**Choices made during implementation:**
- **Untouched fields send stored values:** the edit panel sends the stored value for any field the user did not edit, and the price-book form keeps the stored price for any row the user did not edit. Display rounding (1/16 inch, or a per-foot price converted back from cents per meter) therefore never changes data on its own.
- **A bare number** in a length field is read in the display system's main unit: feet in imperial, meters in metric.
- **Selection** is shared across the plan, the 3D view, and the schedule by `member_id`. The plan shows one plane at a time, chosen by tabs.
- **Edits stay on screen during a reload:** the edit panel stays mounted on the head route while data reloads, so a conflict reload keeps what the user typed (§5).
- **E2E servers:** Playwright starts its own servers on ports 8765 (API) and 5175 (UI), and never reuses running ones.

**Limitations:**
- **Bundle size:** the production bundle is one chunk over 500 kB, mostly Three.js; Vite warns about it. Code-splitting the 3D view is a later optimization.
- **WebGL fallback:** without WebGL, the 3D view shows a text fallback (as in jsdom). Its summary still reports the member count and footprint.
- **Accessibility:** every control is labeled and reachable by keyboard, and the plan has a text alternative. No automated accessibility audit runs yet.
- **Still deferred:** story heights, roof, grid, and section commands (`UI-002`), and direct manipulation in 2D or 3D.
