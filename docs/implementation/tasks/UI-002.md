# UI-002 — Browser editors for the remaining VS-01 commands

**Status:** Done (2026-11-19) — see §12 for implementation notes  
**Owner module:** `frontend/`: presentation only, over the existing API  
**Slice:** VS-01  
**Depends on:** `UI-001` (done)  
**Unblocks:** every editable VS-01 parameter usable from the browser (D043); `TEST-001`  
**Touches:** one schema correction (§12): `GridLineArg.id` is published as an optional string, matching the server.

## 1. Objective and user-visible behavior

UI-001 edits only the footprint and undoes revisions. UI-002 adds browser editors for the other D043 commands, so every editable VS-01 parameter can be changed without the API:

| Command | Edits | Class ([dependencies.md §4.1](../../architecture/dependencies.md#41-vs-01-classification-table-vs01-change-classes-1)) |
|---|---|---|
| `SetStoryHeights` | Level 0 and Level 1 story heights | consequential: preview and confirm |
| `SetGableRoofParameters` | Roof pitch and eave overhang | **routine**: no preview required |
| `SetTimberGrid` | Grid lines on each axis: move, add, remove | consequential |
| `AddSection` | A new rectangular section in the project catalog | **routine** |
| `SetMemberSection` | The section used for every post, or every beam | consequential |

Everything else is unchanged:
- views are paired by revision;
- consequential edits go through preview, the impact dialog, and confirmation;
- conflicts reload the head;
- display rounding never changes stored data on its own.

## 3. Scope

**In scope**

- Editors for the five commands, their client-side argument building, and error placement.
- A notice for committed routine edits, with an undo action that goes through the normal preview.
- Unit, component, and end-to-end tests (§8).

**Non-goals**

- Material commands and per-member edits (D043, D040).
- Grid lines or bay dimensions drawn **in the 2D plan.** The `plan2d` payload does not carry them (artifacts.md §5), and adding them is a GEOM change.
- Direct manipulation in 2D or 3D (dragging lines or edges).
- Deleting or renaming sections. No command exists for either.

## 4. Editor layout (proposal 1)

- **Tabs:** the edit panel becomes tabbed: **Footprint · Stories · Roof · Grid · Sections**. Each tab builds one command type.
- **Head only:** editors appear only on the head, as in UI-001.
- **Typed values are kept:** each tab keeps what the user typed when switching tabs and across conflict reloads. **Reset** returns a tab to the stored values.
- **One command at a time:** a preview or commit disables every tab's submit button until it finishes.
- **Current values:** each tab shows the stored values from the head snapshot, in display units.

## 5. Routine commands (proposal 2)

`SetGableRoofParameters` and `AddSection` are routine. The server accepts them without a preview and still validates them fully (dependencies.md §4.1; FR-12: routine edits propagate automatically).

- **Apply:** the tab's button reads **Apply** and commits directly, with the same `command_id` retry rule as other commits.
- **After a commit:** a notice says "Saved as revision N" and summarizes the change, for example "Pitch 9/12 → 10/12". It offers **Undo**, which runs `UndoToRevision` to the previous head through the normal preview, because undo is consequential.
- **Errors** are placed on fields as for consequential commands.
- **No-ops:** a routine commit can be a no-op (D045). The notice then says nothing changed.

**Alternative:** preview every command, routine ones included. That is more uniform, but adds a confirmation step the classification table says is not needed.

## 6. Editors

### 6.1 Story heights (proposal 3)

- **Fields:** "Level 0 story height" and "Level 1 story height", in display units, using the UI-001 §7 grammar and exact conversion.
- **Derived values:** the stored Level 1 elevation is shown read-only, with the note "Level 1 sits on top of Level 0's story height" (D033, D034).
- **Command:** `SetStoryHeights {story_heights_m: [h0, h1]}`. An untouched field sends its stored value.

### 6.2 Roof (proposal 4)

- **Pitch:** entered as rise per 12 (`9/12`, `9:12`, or `9`) or in degrees (`36.87°` or `36.87 deg`).
  - Rise is converted with `atan(rise / 12)`, degrees with `deg × π / 180`.
  - The server compares pitch with a 1e-9 rad tolerance (D032), so engine-level differences in `atan` cannot move a value across a bound.
  - Re-entering the displayed pitch can still differ from the stored value by one unit in the last place. The untouched-field rule avoids this when the user does not edit the pitch.
- **Overhang:** a length, from 0' to 3'.
- **Display:** pitch as rise/12 to 1/8 and degrees to 0.01°, plus the overhang.
- **Command:** `SetGableRoofParameters {pitch_rad, eave_overhang_m}`, applied directly (§5).

### 6.3 Grid (proposal 5)

The grid is stored as fractions of the footprint width (X) and depth (Y), with line IDs that keep member IDs stable (D042). The editor works in positions instead:

- **One table per axis:** line ID, position from the origin in display units, and the bay length to the next line. Bay lengths are shown read-only, as differences of the displayed positions.
- **End lines** (`fraction` 0 and 1) are fixed. They show 0 and the footprint dimension, and cannot be moved or removed.
- **Edit and remove:** interior lines can be moved or removed.
- **Add a line:** inserts a new line (no `id`) at the midpoint of the chosen bay. The server assigns its ID (§2.1).
- **"Divide into N equal bays":**
  - sets the interior lines to `k / N`;
  - **reuses existing interior line IDs in order**, so their members keep their IDs;
  - adds new lines when N grows and removes the extra lines when it shrinks.
- **Conversion:** a moved line's fraction is `position_m / dimension_m`. An untouched line keeps its stored fraction exactly. For example, `x1` stores `0.3333333333333333`, but 12' / 36' computes to `0.33333333333333337`.
- **Order:** rows are kept sorted by position, so the arguments are ascending. Equal or out-of-range positions are left to the server, which reports them at `args.x_lines[k]` paths. The client does not duplicate D032 (D028).
- **Schematic:** a one-dimensional strip per axis shows the lines to scale. It is labeled "Grid lines (not the plan)" and is drawn only from the editor's own values.
- **Help text:** "Lines are stored as fractions of the footprint. Widening the footprint stretches every bay; bays must stay between 4' and 24'."
- **Command:** `SetTimberGrid {x_lines, y_lines}` with both axes in full (§2.1), through preview.

### 6.4 Sections (proposal 6)

- **Catalog:** the project's `Section` records: label, actual width × depth in display units, and the roles that use each.
- **Add a section:**
  - fields: label (for example `10x12`), actual width, and actual depth, as lengths;
  - command: `AddSection {nominal_label, actual_width_m, actual_depth_m}`, applied directly (§5);
  - a duplicate label is shown on the label field (`DUPLICATE_SECTION_LABEL`, D049).
- **Section per role:**
  - one select per role in `FrameSystem.member_defaults` (`POST` and `BEAM` for Reference House 001), listing the catalog by label;
  - changing one builds `SetMemberSection {role, section_id}` through preview;
  - material stays as it is, because material commands are deferred (D043).
- **Pricing note:** estimate line items are keyed `timber.<ROLE>.<label>`. After a role changes section, its stored price no longer matches and the estimate becomes partial. The tab says so and links to the price-book form, which shows the old row as unused (UI-001 §5.1).

## 7. Errors across editors (proposal 7)

- **Placement:** details are placed with `placeDetails` (UI-001 §5) against each editor's argument paths: `args.story_heights_m[0]`, `args.pitch_rad`, `args.x_lines[k].fraction`, `args.nominal_label`, `args.section_id`.
- **Cross-field errors** (D032, D037): a detail may name fields that another tab edits. For example, widening a three-bay frame past 72' gives a bay-length error at the grid's `x_lines`, with the footprint width and `args.width_m` in `related_paths`. The error stays on the field that was submitted, and the dialog adds "Also see the Grid tab" for each other tab whose stored field appears in the paths.

  The mapping from snapshot paths to tabs comes from the entity kind in the path: `Footprint` → Footprint, `TimberGrid` → Grid, `Level` → Stories, `GableRoof` → Roof, `Section` or `FrameSystem` → Sections.

## 8. Acceptance criteria and automated tests

1. **Unit tests:**
   - pitch parsing for every form, and rejection of malformed pitch;
   - grid argument building:
     - untouched fractions are sent exactly;
     - kept IDs are sent with their fraction;
     - new lines are sent without an ID;
     - ends are fixed;
     - equal bays reuse IDs in order;
     - the arguments are ascending;
   - story-height and section argument building;
   - mapping snapshot paths to tabs.
2. **Component tests** against the captured fixture: each tab shows the Reference House 001 values (36' × 24', 10' and 9', 9/12 and 2', grid at 12' and 12', 8x8 and 8x12) and builds the expected command; routine tabs commit without a preview call.
3. **End to end** (Playwright, real API):
   - **Stories:** change Level 1 to 10' (preview, confirm); the 3D eave rises, and the schedule's post total grows by 12 × 1'.
   - **Roof:** apply 10/12 with no preview; the notice and the new revision appear, and Undo returns to 9/12 through a preview.
   - **Grid:** divide X into 4 bays; the original interior line IDs are kept, and the member count and schedule change.
   - **Contradictory constraints** (AC-06): widening to 76' with 3 bays is rejected with the grid pointer; after dividing X into 4 bays, 76' is accepted.
   - **Sections:** add `10x12`; a duplicate label is rejected on its field; setting `BEAM` to `10x12` updates the schedule, and the estimate shows the old price row as unused.
   - **Untouched fields:** opening and submitting any consequential tab without edits previews as a no-op.

## 9. Implementation guidance (not prescriptive)

- Put each editor in its own component under `src/workspace/editors/`, with argument building as pure functions next to `commands.ts`.
- Extend `useCommandFlow` with a direct `apply(command)` for routine commands, keeping one flow state for the whole workspace.
- Read the head snapshot once per revision (it is already loaded) and derive every tab's stored values from it.

## 12. Implementation notes (2026-11-19)

**Delivered** (`frontend/src/workspace/editors/`):
- `Editors.tsx`: the tab list (arrow keys move between tabs). Every tab stays mounted, so typed values survive tab switches and conflict reloads; a tab is rebuilt from stored values after its own command commits.
- `FootprintEditor.tsx` (the UI-001 edit panel, moved), `StoriesEditor.tsx`, `RoofEditor.tsx`, `GridEditor.tsx` (with the to-scale strips), and `SectionsEditor.tsx`.
- `model.ts`: pure helpers for grid arguments, equal bays, midpoints, grid error placement, and the tab pointers of §7. `useStoredFields.ts`: fields that send stored values until edited. `src/units/pitch.ts`: pitch input.
- `useCommandFlow.apply`: commits routine commands directly. The workspace shows the "Saved as revision N" notice, and its Undo button runs `UndoToRevision` through the preview. The impact dialog adds "Also see the … tab" pointers.

**Tests:**
- **Vitest:** 51 tests (17 new). They cover pitch parsing; grid arguments (untouched fractions sent exactly, moved lines, fixed ends, new lines without IDs, equal bays reusing IDs, error placement); tab pointers; every tab's Reference House 001 values and commands; routine tabs calling `apply` and never `preview`; and field errors.
- **Playwright:** 14 end-to-end tests (6 new):
  - stories: the eave reaches 20' and the post total reaches 240';
  - roof: applied without a preview, then Undo through the preview;
  - grid: four bays, with `x1` and `x2` kept and the new line numbered `x4` by the server;
  - AC-06: 76' is rejected with a Grid pointer, then accepted after adding a bay;
  - sections: add, reject a duplicate, apply to beams, and the old price row shows as unused;
  - untouched tabs preview as no-ops.
- **Backend:** 439 pytest tests, plus the schema and fixture drift checks.
- A manual look at the editors in a browser.

**Choices made during implementation:**
- **Schema correction:** `GridLineArg.id` was published as nullable with a default of `null`, but the server rejects `null` and expects the key to be omitted for a new line (interfaces.md §2.1). The Pydantic field now exports as an optional string. `commands.v1.schema.json`, `openapi.v1.json`, and the generated TypeScript type were regenerated. Validation is unchanged.
- **Errors stay on fields after the dialog closes,** until the next preview or apply. Closing the dialog used to clear them.
- **Grid rows are re-sorted** into the submitted (ascending) order when a grid is previewed, so server error indexes match the rows on screen.
- **Story-height changes reuse the UI-001 flow.** The 3D view's figure now also reports `data-eave-z-m` for tests.
- **Section errors from `SetMemberSection`** are shown under the role selects.

**Limitations:**
- Grid lines are not drawn in the 2D plan; the payload does not carry them (§3).
- The grid editor uses the stored footprint for positions. A width typed in the Footprint tab but not yet committed does not change the grid positions shown.
- Materials, per-member edits, and section deletion remain out of scope.
