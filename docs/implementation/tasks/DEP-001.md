## 1. Objective and user-visible behavior

Make [D056](../../product/decisions/D056-dependency-selectors.md) live, so that AC2-04 holds: **`impacted_artifacts` lists an artifact if and only if its payload changes, and unchanged artifacts are reused for the new revision.**

- **Selectors:** every derivation declares a pure selector. It extracts from the snapshot exactly the values the derivation reads (§4).
- **Fingerprints** hash the selection, the generator, and any external inputs. They no longer include `revision_id` or the whole snapshot (§5).
- **Computed impact:** a preview compares each artifact's fingerprint for the base and for the candidate. `impacted_artifacts` lists the ones that differ, and may be empty (§6).
- **Reuse:** after a commit, an artifact whose fingerprint is unchanged gets a new envelope for the new revision, with the stored payload. It is not derived again (§7).

**User-visible after this task:**
- Previews stop over-reporting. On Reference House 001 v2 (§8):
  - `AddSection` impacts nothing;
  - a pitch-only roof edit impacts the mesh, schedule, and estimate, but not the plan;
  - an overhang-only roof edit impacts the plan and mesh only;
  - changing a role's section leaves the plan unaffected.
- After a commit, unchanged artifacts are `CURRENT` for the new revision at once, with the same payload and fingerprint as before. `UndoToRevision` reuses every payload of its target revision.
- The browser's confirmation dialog lists exactly the impacted artifacts, and says so when there are none (§9.2). Anything more in the browser is `UI-003`.

No payload changes. Generator versions stay `"2"`.

## 4. Selections

### 4.1 Principle (§13 item 8)

A selection contains **exactly the values its builder reads, after the projections the builder itself applies, and nothing else.**

- **"Reads"** means the values that reach the payload. A record a builder resolves only to reach another field (for example the `Building` record, to find the footprint) is not selected. The field it leads to is.
- **"After its projections"** means:
  - the plan selects member and connection positions as plan `x, y`, not 3D points;
  - the mesh selects each member's section dimensions, not its `section_id`;
  - the schedule selects each member's reference-axis length, not its axis.
- **Not in any selection:** the `TimberGrid`, the `FrameSystem` (parameters, member and connection defaults, ID lists), unused `Section` and `Material` records, record `schema_version` fields, `ridge_offset_m`, and revision metadata. Builders read none of them directly. Their effects reach the payload only through the members and connections, which are selected.

The principle is what AC2-04's "if and only if" requires. A value that is selected but does not reach the payload makes its artifact impacted with an unchanged payload. On Reference House 001 v2 that is not hypothetical:

- **Plan and 3D axes** (ART-002 §10): a pitch-only roof edit moves rafters and purlins in `z` only.
- **Schedule and axes** (new here): a joist spacing that keeps five joists per bay span moves every joist, but changes no row of the schedule. Lengths, keys, and IDs are unchanged (§8, measured).
- **Mesh and section IDs:** a section with the same dimensions as the old one under another label changes the schedule, but not the mesh.
- **Estimate and the schedule:** re-identifying grid line `y1` at the same fraction changes every key and ID on that line, so the schedule changes. The aggregates do not, so the estimate does not.

**ART-002 §10 is corrected in two places:**
- `plan2d` does not read the grid or Level 0's story height. Its connections need the entering member's ID (to place the marker on that member's plane), not its key.
- `timber_schedule` reads lengths, which ART-002 §10 listed as "axis (for its length)".

### 4.2 Contents

Arrays of members and connections are in `generation_key` order (code-unit order, as every payload). Numbers are the stored doubles, and a length is computed by the schedule's `reference_length`, exactly as the builder computes it. Canonical form is RFC 8785 (D029).

**`plan2d`**

```json
{
  "footprint": {"origin_m": [0.0, 0.0], "width_m": 10.9728, "depth_m": 7.3152, "rotation_rad": 0.0},
  "levels": [{"id": "<L0>", "elevation_m": 0.0}, {"id": "<L1>", "elevation_m": 3.048, "story_height_m": 2.7432}],
  "roof": {"eave_overhang_m": 0.6096},
  "members": [
    {"id": "…", "generation_key": "frame/x0/y0/level-0/post", "role": "POST", "start_xy_m": [0.0, 0.0]},
    {"id": "…", "generation_key": "frame/axis-x/y0/x0-x1/plane-L1/beam", "role": "BEAM", "start_xy_m": [0.0, 0.0], "end_xy_m": [3.6575999999999995, 0.0]}
  ],
  "connections": [
    {"id": "…", "generation_key": "connection/post-beam/…", "junction_class": "post-beam", "connection_type": "PEGGED_MORTISE_TENON",
     "xy_m": [0.0, 0.0], "entering_member_id": "…"}
  ]
}
```

- **Levels:** in `building.level_ids` order. The plan prints both level IDs, and both elevations as plane heights. Level 1's story height gives `z_eave`, the height of the `eave` and `roof` planes.
- **Posts** carry `start_xy_m` only, because the plan reads only that point. Every other member carries both ends.
- **`entering_member_id`** is `member_ids[1]`. With the members' roles and keys, it fixes the marker's plane, and it cannot raise, as a plane lookup in the selector could.

**`mesh3d`**

```json
{
  "footprint": {"origin_m": [0.0, 0.0], "width_m": 10.9728, "depth_m": 7.3152},
  "levels": [{"elevation_m": 0.0}, {"elevation_m": 3.048, "story_height_m": 2.7432}],
  "roof": {"ridge_axis": "X", "pitch_rad": 0.6435011087932844, "eave_overhang_m": 0.6096},
  "members": [{"id": "…", "generation_key": "…", "role": "BEAM", "start_m": [0.0, 0.0, 3.048], "end_m": [3.6575999999999995, 0.0, 3.048],
               "actual_width_m": 0.2032, "actual_depth_m": 0.3048}],
  "connections": [{"id": "…", "generation_key": "…", "junction_class": "brace", "connection_type": "PEGGED_MORTISE_TENON",
                   "location_m": [0.9144, 0.0, 3.048]}]
}
```

- **No level IDs, no `rotation_rad`:** the mesh prints neither.
- **Section dimensions** are resolved per member from its `section_id`. The ID itself is not selected.

**`timber_schedule`**

```json
{
  "members": [{"id": "…", "generation_key": "…", "role": "POST", "length_m": 3.048,
               "section_id": "…", "nominal_label": "8x8", "material_id": "…", "species": "eastern-white-pine", "grade": null}],
  "connections": [{"id": "…", "generation_key": "…", "junction_class": "joist-beam", "connection_type": "HOUSED_DOVETAIL",
                   "member_ids": ["<receiving>", "<entering>"]}]
}
```

- **Members:** the schedule prints `section_id` and `material_id`, so both are selected, with the section's label and the material's species and grade. Material `name`, `density_kg_m3`, and `provenance` are not read.
- **Connections:** no location, as the schedule has none (ART-002 §6.1).

**`preliminary_estimate`**

```json
{"timber_schedule": {"aggregates": ["…"], "connection_aggregates": ["…"], "assumptions": ["…"]}}
```

- **Upstream projection:** the three lists are copied from the same revision's schedule payload: exactly what `build_estimate` reads, and what D056 names ("the schedule's aggregates and connection counts"). The estimate has no selector over the snapshot.
- **When the schedule is not `CURRENT`:** the value is `{"timber_schedule": null}`. The estimate is then `FAILED` with `UPSTREAM_NOT_CURRENT`, as today.
- **The price book** stays an external input (§5), unchanged.

**Why the estimate uses the schedule's lists, not the schedule's fingerprint:** the fingerprint would be simpler, but it changes whenever any schedule row changes. Re-identifying `y1` (§8) would then list the estimate with an unchanged payload.

### 4.3 What the selections give

Each selection is a pure function of the snapshot, or for the estimate, of the schedule's outcome. With §13 item 9, each builder takes its selection as its only model input, so a builder cannot read anything its selection omits (§16).

## 5. Fingerprints

`input_fingerprint` is `sha256:` plus the lowercase hex SHA-256 of the canonical object:

```json
{
  "selection": { … §4.2 … },
  "generator_id": "plan2d-vs01",
  "generator_version": "2",
  "model_schema_version": 2
}
```

- **The estimate** adds its external inputs, as today: `price_book_id`, `price_book_version`, `as_of`, and `currency`, or `"price_book": null`. Keys starting with `_` (the book's rows) still reach the derivation without being hashed (`registry.py`).
- **Removed:** `revision_id` and `snapshot`.
- **Unchanged:** generator IDs and versions (`"2"`), the `sha256:` format, and the rule that a generator version change makes stored rows `STALE`. No selector version is needed: a selector change changes fingerprints, so stored rows read as `STALE` and are recomputed on read.
- **Not hashed:** `project_id` and `artifact_type`. Reuse is looked up within one project and one type (§7.2), and `generator_id` already names the type.

## 6. Computed impact in the preview

- **Computation:** `impacted_artifacts` is the set of artifact types whose fingerprint for the candidate differs from the fingerprint for the base. Both sides use the project's current external inputs, so a price book never makes an artifact impacted. Output is sorted in code-unit order, as today. It may be empty.
- **No-ops:** a no-op (D045) has equal snapshots, so its list is empty. Today it lists all four.
- **Rejections** are unchanged: a rejected command has no preview.
- **Commit agrees with the preview:** the commit re-runs the command (interfaces.md §4 step 4), and derivation compares the same fingerprints (§7.1). So the artifacts reused for the new revision are exactly those not listed.
- **Where it runs:** in the service, with the candidate from `propose`, so the `model` package does not depend on the derivations. `IMPACTED_ARTIFACTS` and `CandidateChange.impacted_artifacts` are removed from `model/commands/propose.py`.
- **Cost:** the preview computes eight selections. The estimate's needs both revisions' schedule payloads, but only when the schedule's fingerprints differ. Otherwise the estimate's selections are equal too, because the schedule's payload is a function of its selection (§4.3). For the largest supported case, ART-002 §17 measured a schedule build at about 9 ms. The implementation reports the preview's added time for the reference house and the largest case.

## 7. Reuse across revisions

### 7.1 After commit

`derive_revision`, in dependency order, for each artifact of the new revision:

1. computes the fingerprint (§5). The estimate's uses the schedule outcome just stored for this revision;
2. looks for a stored row of the same project and type, with that fingerprint and generator version, and status `CURRENT` or `UNAVAILABLE`;
3. if one exists, stores a **copy** for the new revision: same status, payload, warnings, fingerprint, generator, and `generated_at`; otherwise derives, as today.

- **The envelope is the new revision's own** (D056 item 3): `source_revision_id` and `head` come from the requested revision, as they already do (`_envelope`). AC-07 holds unchanged.
- **`generated_at` is kept** from the row that was copied. It says when the payload was generated, and it makes reuse visible to tests without a new field. *Alternative:* the commit time. That would say when the envelope was made, but it hides reuse.
- **`FAILED` rows are never reused:** the artifact is derived again. Derivation is deterministic, so the result is the same failure, but it costs little and never repeats a failure caused by something outside the selection.
- **Payload copied, not shared:** every revision keeps its own row, as today. No foreign key between rows, no reference counting, and deleting one revision's rows (the "crash" test in `test_artifacts.py`) affects no other revision.

### 7.2 Scope of the lookup

- **Any revision of the same project**, not only the parent. `UndoToRevision` then reuses every payload of its target revision, and a later edit that returns to an earlier state reuses that state's payloads.
- **Never another project's rows.** Payloads carry IDs minted per project, so a hit across projects would need identical IDs. Keeping the lookup inside the project keeps authorization trivially intact.
- **Index:** a new migration adds an index on `artifacts (project_id, artifact_type, input_fingerprint)`. The primary key `(revision_id, artifact_type, input_fingerprint)` is unchanged. The in-memory store gets the same lookup.
- **Choice among several matches:** any matching row will do, because rows with the same fingerprint have the same payload (§10, the reuse check). Implementations take the earliest by `generated_at`, then revision, so tests are deterministic.

### 7.3 On read

Lazy recompute (`get_artifact` for a revision with no matching row, after a crash or a generator version change) uses the same lookup before deriving. The manifest still never derives or copies.

### 7.4 Price books

Unchanged: setting a book changes the estimate's fingerprint, so the head's estimate reads `STALE` and is recomputed on read. Book versions only increase, so an earlier estimate is never reused under a newer book.

## 9. API contract and browser

### 9.1 `impacted_artifacts` (interfaces.md §3)

- **Meaning:** exactly the artifact types whose input fingerprints differ between base and candidate (§6), which is exactly the types whose payload for the new revision will differ. Possibly empty.
- **Type:** an array of the four artifact type keys (`plan2d`, `mesh3d`, `timber_schedule`, `preliminary_estimate`), unique and sorted, instead of strings. OpenAPI and `schema.d.ts` are regenerated.
- **Unchanged:** the commit response. `artifact_statuses` still reports all four types. Reused artifacts are `CURRENT` (or `UNAVAILABLE` for an estimate without a book) with no extra field.

### 9.2 The confirmation dialog (`ImpactDialog.tsx`)

Today it prints "Regenerated: " and the list, so an empty list would show "Regenerated: .". The only change:

- a non-empty list is printed as today;
- an empty list shows "No derived views or reports change."

The dialog keeps the artifact keys. Friendly names, connection counts, and any other dialog change are `UI-003`. A Vitest case covers both forms.

## 10. Testing the if-and-only-if property

D056 item 5 asks for two properties: an artifact is impacted **if and only if** its payload changes, and a reused payload equals a fresh derivation.

**The sequences** (`test_sequences.py`), for every accepted, non-no-op step:

- read the base's and the new revision's four envelopes, as the invariants already do;
- assert that `impacted_artifacts` from the step's preview equals the set of types whose `(status, payload, error)` differs, compared canonically;
- assert that every artifact not listed has the base's `input_fingerprint`, and every listed one a different fingerprint.

The draw gains the cases that make the narrow outcomes reachable: pitch-only and overhang-only roof edits, joist-spacing-only frame edits, `AddSection` with an existing section's dimensions, and a grid line re-identified at the same fraction.

**The invariants** (`invariants.py`), after every step: each of the revision's four payloads equals a fresh build from its snapshot (and, for the estimate, its schedule and the current book), byte for byte. That covers reused and derived payloads alike.

**The golden scenario** (`scenario.py`):

- every committing step is previewed, routine ones included, and its `impacted_artifacts` is recorded in the step entry;
- the scenario asserts the if-and-only-if property against the recorded payload fingerprints of consecutive revisions;
- it asserts that the undo step's four input fingerprints equal revision 2's.

**Targeted tests** (`test_artifacts.py`, `test_project.py`):

- each row of §8, from the created house;
- after `AddSection`, no derivation runs (a counting stub registry), and the four rows of the new revision equal the base's, `generated_at` included;
- a `FAILED` row is derived again rather than copied;
- a reused row survives the deletion of the revision it was copied from;
- lazy recompute finds a matching row of another revision;
- the lookup never returns another project's row;
- a generator version bump still makes rows `STALE`.

## 14. Acceptance criteria and automated tests

1. **Exact impact (AC2-04):** in the sequences, for every accepted, non-no-op step, `impacted_artifacts` equals the set of types whose outcome differs between base and new revision, and only those types' fingerprints differ.
2. **Measured cases (§8):** each row of the §8 table gives exactly that list, from the created house.
3. **Empty impact:**
   - `AddSection` and a no-op list nothing;
   - `SetConnectionType` for a class with no connections lists nothing and still requires confirmation;
   - a price-book change has no preview, and still makes only the head's estimate `STALE` (§7.4).
4. **Reuse (D056 item 3):**
   - after a commit, every artifact not listed has a row for the new revision with the base's payload, fingerprint, and `generated_at`, and no derivation ran for it;
   - its envelope names the new revision, with `head: true`;
   - `UndoToRevision` reuses all four rows of its target.
5. **Reused equals fresh (D056 item 5):** after every step of the sequences and the golden scenario, each payload equals a fresh build from the revision's snapshot, byte for byte.
6. **Failures:** a `FAILED` row is never copied. An estimate whose schedule is not `CURRENT` stays `FAILED` with `UPSTREAM_NOT_CURRENT`.
7. **Lookup scope:** reuse finds rows of other revisions of the same project, never another project's rows, and survives the deletion of the source revision's rows.
8. **VS-01 still holds (AC2-05):**
   - AC-07: an envelope always names its own revision; the manifest of an older revision reports its own rows;
   - artifacts.md §10 tests 1–8 pass, test 5 with `SetFootprintDimensions`;
   - a generator version bump makes stored rows `STALE`;
   - the lazy recompute after deleted rows still works.
9. **Fingerprints (§5):** the stored fingerprint equals the hash of the §5 object, and contains no `revision_id`. Two revisions with equal selections have equal fingerprints.
10. **Golden record (§11):** the regenerated record differs only in `input_fingerprint` values and the added `impacted_artifacts`, and its fingerprints repeat as §11 states. `golden.py --check` passes.
11. **Contract:** preview responses validate against the regenerated OpenAPI, with `impacted_artifacts` items from the four type keys. The drift checks pass.
12. **Browser (§9.2):** Vitest covers the empty and non-empty dialog lists.

## 15. Errors, security, and migration

- **Errors:** none new. A selector must not raise for a snapshot that passed validation. Lookups go by ID, and the plan's selector stores the entering member's ID rather than computing a plane (§4.2). A selector that raises anyway is an unexpected error: 500 `INTERNAL` for a preview, `FAILED` with `DERIVATION_FAILED` for a derivation.
- **Security:** no new endpoints or permissions. Reuse never crosses projects (§7.2), so owner-only access (D050) is untouched. Logs record reuse without project content (dependencies.md §9).
- **Migration:** an index migration only (§7.2). Stored rows of the old fingerprint form read as `STALE` and are recomputed on read. No data is converted (D055).
