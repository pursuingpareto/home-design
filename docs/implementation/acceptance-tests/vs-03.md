The acceptance criteria (§15) and tasks (§19) are proposed for the recommended answers and will be revised as each proposal is decided. Approved judgment items are recorded as decisions from D091.

**Builds on:** VS-02b, complete and verified by `TEST-003` ([vs-02b.md](vs-02b.md), [vs-02b-traceability.md](vs-02b-traceability.md), [D090](../../product/decisions/D090-vs02b-budgets-and-named-wall-case.md)).

## 1. Where VS-02b leaves the product

Measured on `main` at `b903dd9` (2026-11-24), in-process with the memory store, on an otherwise idle Apple A18 Pro; scripts in the hand-over note (§20).

- **Model:** schema version 3. Reference House 001 v3 has 651 entities plus the building: 48 authored records (footprint, levels, roof, grid, frame and wall systems, 9 sections, 9 materials, 2 assembly definitions, 20 openings) and 604 generated ones (193 members, 312 connections, 20 walls, 79 wall framing pieces). Its canonical snapshot is **271,715 bytes**; the authored records alone are **35,901 bytes**.
- **Commands:** 14 typed commands (interfaces.md §2): `CreateReferenceProject`, the eight frame commands, `AddSection`, `UndoToRevision`, and the four wall commands. Arguments are strict, and their JSON Schema is committed as [`commands.v1.schema.json`](../../architecture/schemas/commands.v1.schema.json) (D028).
- **Preview and commit:** one command per preview and per revision. A preview is non-mutating and returns the semantic diff, the generated-record diffs, the exact `impacted_artifacts`, and a stateless token (D047) that binds the commit to project, actor, base revision, and `command_hash`. Consequential commands need the token; routine ones commit directly with undo (`vs02b-change-classes-1`).
- **Chaining:** a preview against any base other than the head is a `REVISION_CONFLICT` (measured: previewing a second command on the first one's candidate revision is rejected). So the API cannot preview a sequence of commands today. Inside the server, `propose()` is a pure function of a snapshot and a command, so a sequence can be validated in memory, each step on the previous candidate (measured below).
- **Measured costs** (median of 5; previews through the service, including `impacted_artifacts`):

  | Case | Time | Preview body |
  |---|---|---|
  | `SetOpening` preview | 155 ms | about 1.5 kB |
  | `SetWallAssembly` preview (to stud infill) | 175 ms | about 47 kB |
  | `SetFootprintDimensions` preview (to 40') | 168 ms | about 62 kB |
  | One `propose()` step (`SetOpening`) | 92 ms | — |
  | Three chained steps (`SetWallAssembly`, `SetOpening`, width) | 336 ms | — |
  | 20 chained `SetOpening` steps | 1,848 ms | — |
  | 50 chained `SetOpening` steps (median of 3) | 4,689 ms | — |

- **Audit and history:** every commit attempt is an append-only `operations` row (actor, command, hash, base, result, classification, MODEL-004 §4.5). Revisions record their parent, sequence, and time; the history route shows each revision's `command_type`. Nothing records a revision's **source** (a person in the editors, or an AI proposal) beyond the actor (FR-01 names "author/source").
- **Checks:** scripts/check.sh passes on this commit (1,006 backend tests in 14 min 36 s, 137 Vitest tests, 31 Playwright tests; 18 min in all), with three traceability matrices, the golden scenario, property sequences, and the D063 and D090 budgets.

Deliberately absent: any `ai` module code (overview.md lists it; interfaces.md §1 has it as "future: produces typed proposed operations; has no direct persistence access"), any AI provider dependency, any route for proposals (interfaces.md §10 lists "natural-language proposals" as a deferred contract, to be added "via separate versioned design documents"), and any record of goals or structured requirements (workflows.md, step 2).

## 2. What the documents already fix

These are not open questions; every option below keeps them.

- **One change path.** AI changes are typed commands from the command set and pass through the same server-side parsing, validation, classification, and transaction as manual edits (building-model.md §1 item 3; workflows.md; overview.md "AI suggestions cannot bypass" permission checks and validation). No arbitrary expressions, geometry scripts, or SQL (interfaces.md §8).
- **No persistence access.** The `ai` module produces proposed operations and never writes the model (interfaces.md §1).
- **Explicit, inspectable, reversible proposals** (principle 5). Nothing the AI suggests changes the model until a person approves it.
- **Classification is the server's.** "Future AI may suggest classification but cannot override it" (dependencies.md §4).
- **Honest assurance.** Every output stays preliminary, with no structural, code, or permit claim (AC-08, principle 7, FR-10). An AI explanation is not an analysis.
- **Do not silently redesign** (principle 3): an approximation, a partial answer, or an unsupported request is said, not hidden.
- **Traceability** (principle 6): an applied proposal is tied to its revision and inputs.
- **Owner-only projects** (D050): only a project's owner can read or write it, until VS-06 adds roles.

## 4. Scope options (proposal 1)

**Option 1: "Collaborator proposals with approval"** (**recommended**): themes A, B, C.

- A request produces one proposal over the existing commands (except creation and undo, §8), or a "no change" answer that says why. The user approves or rejects it; an approved proposal is applied atomically as one revision. Every proposal and decision is recorded.
- **Why:** it delivers principle 5 and D012's default mode end to end on the model VS-02b left, without new model kinds. Every request it can serve is one the editors already serve, so validation, preview, and undo already exist.
- **Cost:** the AI can only do what the 12 editing commands do. "Add a bathroom" or "make it L-shaped" get a clear "not supported yet", which is honest but limits the demonstration.

**Option 2: "Collaborator and assistant":** Option 1 plus theme D.

- Questions get answers in words. A homeowner's first questions are often questions, not edits.
- Answers are free text about engineering-adjacent facts ("is this enough insulation?"). Keeping them honest needs their own rules: grounded in the model and its artifacts, never a performance or code statement. That is a larger testing problem than proposals, whose effect the server computes.

**Option 3: "Single-command proposals":** themes A, B, C with exactly one command per proposal.

- Reuses preview and commit unchanged; no composite command (proposal 2).
- Many ordinary requests need several commands: "remove every window" is 19 `RemoveOpening` steps on the reference house (measured), and "40 feet wide with a 10/12 roof" is two. The user would approve them one at a time, with intermediate revisions the AI did not intend.

**Option 4: "Goals to proposals":** Option 1 plus theme E.

- Starts workflows.md at step 1–2: goals are captured as records, and proposals cite them.
- No artifact or analysis reads goals until VS-04, so the records would be stored but not used. Better designed with VS-04's comparisons.

Proposals 2–8 build on Option 1. Option 2 would add one more judgment item (answer grounding), and Option 3 would drop proposal 2.

## 5. Cross-cutting concerns (any option)

- **The snapshot schema does not change.** No new model kind is needed for Option 1, so `model_schema_version` stays 3, and no fixture or golden snapshot is regenerated. Proposal records are project data outside the snapshot, in a new database migration (`0006`), like price books (`0003`).
- **A new major dependency.** An AI provider is the project's first external service at request time. AGENTS.md requires its tradeoffs to be explained before it is introduced (proposal 5).
- **Non-determinism.** The engine's output is not reproducible, but everything after it is: parsing, validation, preview, IDs, and commit are deterministic given the proposed commands. Tests separate the two (proposals 5 and 8).
- **Data leaves the server.** Sending project content to a provider is a new privacy surface. Open question 8 (security and privacy requirements) is still open (proposal 6).
- **Prompt injection.** Project text that users write (section labels, assembly labels) reaches the engine. It can only produce commands, which are validated and need approval, but the explanation text it writes is shown to the user. The routine items keep injection from widening what a proposal can do (item 9).
- **Bounds on openings** (roadmap open item; [D090](../../product/decisions/D090-vs02b-budgets-and-named-wall-case.md), [TEST-003](../tasks/TEST-003.md) §8.2). Openings have no bounds beyond the fit, so a valid snapshot can exceed D063's 2 MB ceiling. VS-03 does not change that: a proposal uses the same commands and fits as the editors. It does make many openings cheaper to request ("add a window to every bay"), so the product owner may want to settle the bounds before or beside VS-03. No document calls for folding it into this slice, so it stays a task of its own. The step cap in proposal 2 limits one proposal's size, not the model's.
- **Engineering boundary unchanged:** VS-04 owns analysis. An AI that says "this is structurally fine" would contradict AC-08; item 12 covers it.

## 7. Routine items (9–15)

They follow from earlier decisions and documents, so they need no decision record of their own; the task files carry them out.

9. **Typed commands only, validated as manual edits** (§2). The engine's output is parsed by the same strict parser as any request body (API-001 §5) into command envelopes, then validated and previewed by the same code. Anything that does not parse is not a proposal. The engine runs as the requesting actor, only on projects that actor may read (D050), and has no store access (interfaces.md §1). Commands it may propose are listed in §8.
10. **Explicit approval bound to the preview** (principle 5, D047). Every proposal is applied only by the owner's explicit approval of its preview, **whatever the classification of its steps**: an all-routine proposal still needs approval, because the AI, not the user, chose the edit. The preview token binds the approval to the project, actor, base revision, and the proposal's exact steps (through `command_hash`). A proposal whose base is no longer the head is never applied to the new head (`REVISION_CONFLICT`, dependencies.md §5); the user asks again. An expired token is refreshed and re-confirmed, as the browser does today (UI-001).
11. **Provenance** (principle 6, FR-01). The operation that applies a proposal records the proposal's ID; the revision history marks revisions made from proposals and links to the proposal; the proposal record names the revision it produced. The audit log (MODEL-004 §4.5) also records proposal requests and decisions. Routine logs carry no request or explanation text, as they carry no snapshot content today (dependencies.md §9).
12. **Labeled and preliminary** (AC-08, principle 7). Every proposal carries `PRELIMINARY_UNVERIFIED` and a new warning (working name `AI_GENERATED_UNVERIFIED`: "This proposal was written by an AI. Its explanation has not been checked; the listed changes are what the server computed."). The browser shows the AI's text as the AI's, and the server's diff and impact as the server's. Artifacts of a revision made from a proposal are labeled exactly as any other revision's: `suitability: "preliminary"`, `claims.*` false. The engine is instructed never to claim structural adequacy, code compliance, or performance, and the evaluation set (proposal 8) includes requests that invite such claims.
13. **Undo, schema, classification, and design document.** An applied proposal is one revision (proposal 2), so one `UndoToRevision` reverts it (D044). The snapshot schema does not change (§5). The classification table gains the composite command as a new version, `vs03-change-classes-1`, keeping every row of `vs02b-change-classes-1` (dependencies.md §4.1). The proposal routes, records, and engine interface are specified in a new versioned architecture document, `docs/architecture/ai-proposals.md`, as interfaces.md §10 requires, and interfaces.md §1, §5, §7, and §10 link to it.
14. **Browser.** The proposal panel uses the existing flows: review in the confirmation dialog pattern (UI-001, with D088's warning block for removed openings), apply with the existing retry and conflict handling (`useCommandFlow`), and undo from the history. Layout, labels, and wording are set in the UI task file.
15. **Traceability and budgets.** A separate `vs-03-traceability.md`, one row per criterion bullet, checked against this file's IDs and wording, as D063 set for VS-02 and D090 for VS-02b; the earlier matrices stay enforced. CI runs only the deterministic engine (proposal 5). D063's per-payload ceilings apply to proposal bodies, and the server's part of a proposal (validation, preview, commit, excluding the provider's time) gets time ceilings set from measurements in D063's form, with its stop-and-report rule.

## 8. Proposal 2: applying a proposal

**Question:** how a proposal of several commands is previewed, approved, and applied, and what it may contain.

**Recommendation:**

- **One composite command, `ApplyProposal {proposal_id}`** (working name). The proposal's steps are stored, immutable, with the proposal (proposal 3); the command reads them as `UndoToRevision` reads its target (D044), so `propose()` stays pure. The steps run in order, each on the previous step's candidate, and the result is **one candidate, one preview, one revision, and one operation**. Measured: three chained steps take 336 ms in-process (§1).
- **All or nothing:** approval applies every step or none. A step that fails rejects the whole command, naming the step by its index (path syntax set in the task file).
- **Each step is validated,** on its own candidate, exactly as when sent alone. It reuses `propose()` unchanged and its errors name the step and field. *Consequence:* an order of steps whose intermediate state is invalid (two openings swapping positions) is rejected, and the engine must order its steps. Validating only the final candidate would accept it and cost one validation instead of one per step, but its errors could not name a step.
- **Combined preview:** `changes`, `members`, `connections`, `walls`, and `wall_framing` compare the base with the final candidate (a record added and then removed inside the proposal is not listed), and `impacted_artifacts` is exact over the whole proposal (AC2-04). The preview also lists the steps in order, with each step's classification.
- **Classification:** consequential always (item 10), so approval goes through the preview token.
- **What a step may be:** any command of `vs02b-change-classes-1` except `CreateReferenceProject` (the project exists) and `UndoToRevision` (undo stays the user's: "reversible" means the user can reverse the AI, not that the AI chooses which history to restore). `AddSection` is allowed, so "use 10×10 posts" can add the section and then set it. A price-book change is not a command and is not proposable.
- **No references to records the proposal creates:** a step may reference only records in the base. IDs a step creates are minted from the proposal's command (D041) and are not known to the engine. "Add a window and then move it" is one `AddOpening` with the final position.
- **A step cap: 20 steps** (strawman). Measured: 20 chained `SetOpening` steps take 1.8 s and 50 take 4.7 s in-process, and the command runs at preview and again at commit (MODEL-004 §4.3). 20 covers "remove every window" (19) and one opening per wall on the reference house (20). The cap limits a proposal's size and time, not the model's (§5).
- **No-op:** a proposal whose final candidate equals the base is reported as "no change" and not offered for approval (D045).

**Alternatives:**

- **One revision per step,** committed in sequence under one approval: no composite command, but not atomic (a later step can fail after earlier ones are committed), with intermediate revisions in the history and several undos to revert.
- **`ApplyProposal {steps}`** carrying the steps in its arguments: self-contained, but any client could then send a batch labeled as a proposal, and provenance would rest on the client.
- **Choosing steps:** the user approves a subset. Each subset needs its own validation and preview, and later steps may depend on earlier ones. A follow-up request ("only the south windows") gives the same result through a new proposal (proposal 3).
- **Editing a step's values before approval** (D013's "precise visual controls"): the result is no longer the AI's proposal, so its provenance needs a third state. Applying the proposal and then using the editors gives the same result with existing tools.
- **Rebasing a stale proposal** onto the new head automatically: it would apply commands to a model the AI did not see, which principle 3 warns against. Asking again re-reads the head.

## 9. Proposal 3: proposal records and follow-up requests

**Question:** what is stored about a request and its proposal, its lifecycle, and how follow-up requests ("smaller, please") work.

**Recommendation:**

- **A stored, immutable proposal record** per request: project, requesting actor, base revision, request text, the engine and its version (provider and model name for an LLM adapter), the outcome (`proposal`, `no_change`, or `invalid`, proposal 7), the explanation, the steps, the repair attempts' errors, and timestamps. Records are append-only, as revisions and operations are (D026).
- **Lifecycle as append-only events:** `open` → `applied` (with the revision), `rejected` (by the user), or `superseded` (the head moved, or a follow-up replaced it). Expiry follows from the base: once the head moves, the proposal cannot be applied (item 10), and the list shows it as superseded.
- **Follow-up requests:** a request may name the proposal it follows. The engine then sees that thread's earlier requests, explanations, and steps, and nothing from other threads. A follow-up creates a new proposal; the earlier one becomes superseded. There is no free chat history beyond threads.
- **Routes** (in the design document, item 13): create a proposal from a request; list a project's proposals; read one; reject one. Applying is the existing commit route with `ApplyProposal` and its token.
- **Retention:** request text is project content, kept with the project. Deleting it is not possible while records are append-only; retention and deletion are left to open question 8, and the design document says so.

**Alternatives:**

- **Stateless proposals,** like previews (D047): nothing stored until applied, and the applying operation records the request and steps. Cheaper and nothing to retain, but rejected and invalid proposals leave no record, the engine's track record cannot be audited, and a reload loses the open proposal.
- **A free conversation per project:** every earlier request informs the next. Closer to a chat assistant, but harder to explain which inputs produced a proposal (principle 6), and larger engine inputs.
- **Storing no request text:** only the steps and explanation. Less sensitive data, but the proposal could not be traced to what the user asked for.

## 10. Proposal 4: inspecting a proposal

**Question:** what the user sees before approving.

**Recommendation:**

- **The proposal card:** the request, the AI's explanation (labeled, item 12), and the steps in plain words with their values in the units switch's system ("Set the footprint to 40'-0" × 24'-0""), each with its classification.
- **The server's impact,** in the existing confirmation dialog's form: counts of added, removed, and updated members, connections, walls, and wall framing; changed fields; removed openings (D088); and the impacted artifacts.
- **Before and after in 2D and 3D:** the browser can show the proposal's `plan2d` and `mesh3d`, derived on request for the final candidate and not stored (a new read route on the proposal). The builders are pure functions of their selections (D061), so this needs no new derivation. Measured: a width preview is 168 ms; deriving the two views adds their builders' time, measured by the task. Schedules and the estimate are not previewed: the dialog says which of them change.

**Alternatives:**

- **Diff and dialog only:** no new route. A homeowner reads counts and field names, not geometry; "add two windows" is hard to check without seeing where.
- **Every artifact for the candidate,** schedules and estimate included: a full before-and-after comparison, closer to VS-04's alternatives (FR-09). More routes and payloads, for a comparison that VS-04 will specify properly.
- **Highlight only:** the current views highlight the records a proposal touches (`highlight.ts` exists). Cheap, but it shows where, not what: an added window or a moved wall is not drawn.

## 11. Proposal 5: the AI engine

**Question:** how the server gets proposals from natural language, which provider, and what happens when it is not available.

**Recommendation:**

- **A provider-neutral `ProposalEngine` interface** in the `ai` module (overview.md: "provider-neutral AI integration"): given the request, the model context (proposal 6), and the thread, it returns an explanation and command envelopes, or a "no change" answer. Only adapters know a provider.
- **Two engines in VS-03:**
  - a **scripted engine**: deterministic, offline, mapping a fixed set of requests to fixed outputs (including invalid and unsupported ones). It runs in every test, in CI, in the e2e tests, and in local development without a key;
  - **one LLM adapter**, for a provider and model **the product owner names**, using the provider's structured or tool-calling output, constrained to the exported command schema (`commands.v1.schema.json`, D028). Its key comes from server configuration and is never logged or returned, as the preview key (D047).
- **Off unless configured:** with no adapter configured, proposal routes return a stable error (working name `AI_UNAVAILABLE`, 503) and the browser hides or disables the panel. Everything else works. A provider outage or timeout returns the same code, and nothing is stored as a proposal.
- **Synchronous, with a timeout:** the create route waits for the engine, with a server-side timeout (strawman: 60 s) and no job queue, as artifacts are derived synchronously today (ART-001). Asynchronous proposals come with workers later.
- **No live provider in CI:** CI has no key, and the LLM adapter is tested against recorded provider responses. Live runs are the evaluation (proposal 8).
- **Cost control:** a configurable per-actor limit on requests per hour (strawman: 30). D050 deferred rate limiting in general; this one exists because each request costs money.

**For the product owner:** which provider and model the adapter targets, and whether development may use a live key.

**Alternatives:**

- **Scripted engine only in VS-03:** fully deterministic and free, with the LLM adapter in a later slice. The slice would prove the approval workflow but not "natural language".
- **A provider built in directly,** without the interface: less code now, but it breaks "replaceable behind clear interfaces" (AGENTS.md principle 5).
- **A self-hosted open-weights model:** no data leaves the operator's infrastructure, but hosting is open (open question 8), and quality for structured output is unmeasured.

## 12. Proposal 6: what the AI sees

**Question:** which project data the engine receives, and what leaves the server.

**Recommendation:**

- **Authored records and a summary, not the whole snapshot.** The engine receives the authored records (48 on the reference house, 35,901 bytes canonical, against 271,715 for the whole snapshot), plus a generated summary: counts per kind, each wall's key, story, and elevation side (as the assembly schedule reports them, ART-003), each opening's wall, kind, size, and offset, and the supported ranges that bound arguments (D032, D034, D077). Members, connections, and wall framing are summarized by count, not listed: they are generated, and no command edits one directly.
- **The command catalog:** the 12 proposable commands with their schemas and short descriptions, and the D054 connection catalog for `SetConnectionType`.
- **Never sent:** the price book, other projects, actor identities, tokens, and audit rows. Request text and thread history are sent, because they are the request.
- **Disclosed to the user:** the panel says that the request and the project's design data are sent to the named provider.

**Alternatives:**

- **The whole canonical snapshot:** the engine sees every member, at about 7.6 times the bytes; generated records add nothing a command can change.
- **Request only, no model data:** nothing leaves but the text, but the engine cannot name a wall, opening, or section, so most requests could not be expressed.
- **Artifacts too** (schedules, estimate): lets the engine answer "what does it cost", which is Option 2's assistant mode.

## 13. Proposal 7: invalid, partial, and unsupported requests

**Question:** what happens when the engine's commands do not validate, when only part of a request is supported, and when none of it is.

**Recommendation:**

- **Repair, bounded:** when a proposal's steps fail parsing or validation, the server returns the structured errors (paths, codes, and messages, interfaces.md §7) to the engine and asks once more, up to **2 repair attempts** (strawman). Measured examples: "90 feet wide" fails with `OUT_OF_SUPPORTED_RANGE` on the footprint and the bays (D032); a window 0.3 m from a post fails with `OPENING_CROSSES_BRACE` (D076). Each attempt's errors are stored with the proposal (proposal 3).
- **Invalid after repair:** the outcome is `invalid`, shown as "the AI could not produce a valid change" with the last errors in words. It is never offered for approval.
- **Partial:** a request with supported and unsupported parts ("add a window and a bathroom") gets a proposal for the supported part, and the explanation names the unsupported part. The proposal record keeps the unsupported part as a separate field, so the browser can show it as a notice, not as prose the user might miss.
- **Unsupported:** no supported change → `no_change` with the reason, for example "rooms are not part of the model yet". Never an approximation presented as the request (principle 3).
- **Never silently adjusted:** the server never changes a step's values to make it fit (no clamping to ranges, no moving openings), as D069 forbids for frame edits.

**Alternatives:**

- **No repair:** the first invalid output is the answer. Cheaper and simpler; measured examples show that ordinary requests hit range and fit rules, which the errors make easy to correct.
- **Offer the valid steps of an invalid proposal:** the user approves what validated. The remainder may depend on the failed step, and the result is something nobody asked for.
- **Ask a clarifying question** instead of proposing: closer to a conversation, but it needs Option 2's answer mode.

## 14. Proposal 8: accepting the AI's quality

**Question:** how VS-03 decides that the AI is good enough, given that its output is not deterministic.

**Recommendation:**

- **CI gates only deterministic behavior,** with the scripted engine: parsing, validation, composite preview and commit, approval, provenance, the browser flows, and the AC3 criteria.
- **An evaluation set,** run on demand against the configured provider: about 20 reference requests on Reference House 001 v3, each with its expected outcome (the step types and argument values within 1e-6 m, `no_change`, or a named partial). Strawman requests:
  - supported: switch to stud infill; 40'-0" wide; a 10/12 roof; 10×10 posts (adds the section); engineered connections for knee braces; remove the windows on the north wall; the Level 1 north windows widened to 4'-0"; 30" joist spacing;
  - range and fit: 90'-0" wide; a window across a brace;
  - partial and unsupported: a bathroom; an L-shaped plan; "is this up to code?"; "is the frame strong enough?";
  - injection: a section label that contains instructions.
- **Reported, not gated:** each run records the provider, model, date, and per-request results in the traceability document. The product owner sets an acceptance bar after the first measured run, as D063 set ceilings after measuring.

**Alternatives:**

- **A gated pass rate in a scheduled job:** catches provider regressions automatically, but needs a key in CI and a threshold before any measurement exists.
- **No evaluation set:** only contracts. The slice would then say nothing about whether the AI understands requests.

## 15. Acceptance criteria (proposed)

For Option 1 with the recommendations; revised as proposals are decided.

- **AC3-01: request to proposal.**
  - The owner of a project describes a change in words; the system returns a proposal (an explanation, ordered typed steps, and the server's preview of their combined effect), a `no_change` answer with its reason, or an `invalid` outcome with the errors.
  - Making a proposal changes nothing: no revision, no head change, no artifact.
- **AC3-02: one change path.**
  - Every step is a command of the command set except creation and undo, parsed and validated exactly as when a person sends it. An invalid step is never offered for approval.
  - Nothing the engine returns reaches the model except through `ApplyProposal` (item 9).
- **AC3-03: explicit, atomic approval.**
  - A proposal is applied only by its owner's approval of its preview, bound by the preview token, whatever its steps' classification.
  - It applies all its steps as one revision and one operation, or none.
  - A proposal whose base is not the head is never applied (`REVISION_CONFLICT`); a rejected proposal changes nothing.
- **AC3-04: inspectable.**
  - The preview lists the steps, the combined changes, and exactly the impacted artifacts, and the commit produces exactly that diff and those IDs (D041, AC2-04).
  - The proposal's `plan2d` and `mesh3d` can be shown before approval (proposal 4).
- **AC3-05: reversible.** One `UndoToRevision` restores the revision before an applied proposal, with original IDs (D044).
- **AC3-06: traceable.** Each proposal record names its request, engine and version, base revision, steps, outcome, and decision; the revision made from it names the proposal; the audit log records requests and decisions.
- **AC3-07: honest.**
  - Every proposal carries `PRELIMINARY_UNVERIFIED` and `AI_GENERATED_UNVERIFIED`; its explanation is shown as the AI's.
  - Unsupported parts of a request are named, never approximated silently, and no value is adjusted to fit.
  - No proposal claims structural adequacy, code compliance, or performance (checked in the evaluation set).
- **AC3-08: safe and available.**
  - The engine acts only for the requesting owner and receives only the data in proposal 6.
  - Without a configured engine, or when the provider fails, proposal routes return `AI_UNAVAILABLE` and every other feature works.
- **AC3-09: earlier slices still hold.** AC-01 to AC-09, AC2-02 to AC2-09, and AC2b-01 to AC2b-11 pass unchanged.
- **AC3-10: browser.** A request can be typed, its proposal reviewed (explanation, steps, impact, views), approved, rejected, or followed up, and an applied proposal undone; the history marks revisions made from proposals.
- **AC3-11: quality is measured.** The evaluation set has been run against the configured provider and its results recorded (proposal 8).
- **AC3-12: traceability.** A traceability matrix covers AC3-01 to AC3-11; the golden scenario, property sequences, budgets, and CI run them with the scripted engine.

## 17. How the criteria are traced and tested

- **Matrix:** `vs-03-traceability.md`, one row per criterion bullet of §15, checked by `test_traceability.py` against this file's IDs and wording, as for VS-02 and VS-02b (D063, D090).
- **Golden scenario:** the scripted engine extends the golden scenario with requests that produce a single-step proposal, a multi-step proposal (approved, then undone), an all-routine proposal (still needing approval), a stale proposal (`REVISION_CONFLICT`), an invalid one (after repair), a partial one, and an unsupported one. Their previews, IDs, and revisions are golden records (D041 makes them deterministic).
- **Property sequences:** random proposals of 1 to 20 valid and invalid steps drawn from the existing command strategies; checked: `ApplyProposal`'s candidate equals applying its steps one at a time; the preview equals the commit; impact is exact (AC2-04's if-and-only-if property); a rejected or failed proposal leaves the head unchanged; identity invariants from TEST-002 and TEST-003 hold.
- **Contract tests:** the engine has no store access (an import-boundary test: the `ai` module imports nothing from `project`; no such test exists yet for other modules); the price book and other projects are never in the engine's input; the LLM adapter maps recorded provider responses, including malformed ones, to proposals or errors.
- **Budgets:** proposal and preview bodies under D063's ceilings; time ceilings for the server's part of a 20-step proposal (preview and commit), set from CI measurements with D063's stop-and-report rule.
- **Browser:** component tests with the scripted engine behind the fake API; one end-to-end flow (request, review, approve, undo) against a server with the scripted engine.
- **Evaluation:** proposal 8's set, run by hand, recorded in the matrix as reported results.
