# Interfaces and contracts — design specification

**Version:** 0.2 draft · **Status:** Proposed API contracts for VS-01; subject to implementation review.

## 1. Ownership and boundaries

- `project`: identity, authorization, current head, revision persistence.
- `model`: schema, typed operations, candidate snapshots, validation.
- `timber`: deterministic member generation and stable generation keys. Rules live in a registry keyed by `generation_rule_version`; each rule provides `generate` and `conformance`. Model validation reaches a rule only through the registry, `timber` depends only on model types, and the model module contains no rule logic. New rule versions are added by registration ([TIMBER-001](../implementation/tasks/TIMBER-001.md) §6, §10 item 5).
- `geometry`: derive 2D/3D render data from semantic snapshots; never mutate authoritative model.
- `dependencies`: preview impacted outputs, invalidate, schedule, and track artifact freshness.
- `estimating`: preliminary quantities and cost using explicit dated price inputs.
- `ai` (future): produces typed proposed operations; has no direct persistence access.

No module may write another module's private tables. Cross-module communication uses typed calls or durable events; one application-level command handler owns transactions.

## 2. Command envelope

```json
{
  "command_id": "b8f9d645-5a10-4eb5-b2ca-38ce46e5d4aa",
  "project_id": "b9531a91-9f14-49b9-8b1e-7eac1960c770",
  "base_revision_id": "ab4c88f3-f5e9-47dd-8ee0-4c7a19a0b6cf",
  "type": "SetFootprintDimensions",
  "args": {"width_m": 13, "depth_m": 9}
}
```

**Creation envelope:** `CreateReferenceProject` has no project or base revision yet, so it uses `{"command_id": "<uuid>", "type": "CreateReferenceProject", "args": {}}`, sent to `POST /api/v1/projects`. The server assigns the project ID (random UUIDv4, stored with the idempotency record, [D041](../product/decisions/D041-deterministic-id-minting.md)). The initial snapshot is built from Reference House 001:

- Non-member records are copied with new IDs minted from creation key `"template/" + fixture record ID`, and every reference is rewritten to use them.
- All members are then generated by `vs01-post-beam-1`, with IDs minted from `"generation/" + generation_key`.
- `parent_revision_id` is `null`.
- The result equals the fixture in every value and generation key, with generated member coordinates within 1e-6 m ([generation-rules.md, "Numeric evaluation"](../reference-projects/vermont-timber-house/generation-rules.md#numeric-evaluation)); only IDs and revision metadata otherwise differ.

Approved from [MODEL-003](../implementation/tasks/MODEL-003.md) §10, item 9.

Actor identity is derived from authenticated server context, not trusted from the client body. `command_id` is an idempotency key scoped to project and actor; for `CreateReferenceProject`, which has no project yet, it is scoped to the actor. Only commits that succeed (a new revision or a no-op) reserve a `command_id`. A rejected attempt is audited but does not block a retry under the same ID ([MODEL-004](../implementation/tasks/MODEL-004.md) §4.4). IDs a command creates (entities, revision, operation) are UUIDv5 values derived from the project, actor, `command_id`, and a per-record creation key, so a preview reports exactly the IDs its commit will create ([D041](../product/decisions/D041-deterministic-id-minting.md)). A repeated key with a different payload (compared in canonical form, [D029](../product/decisions/D029-canonical-json-rfc8785.md)) returns `IDEMPOTENCY_CONFLICT`.

VS-01 command set ([D043](../product/decisions/D043-vs01-command-set.md)); arguments are strict, with all listed keys required and unknown keys rejected:

| `type` | `args` |
|---|---|
| `CreateReferenceProject` | `{}` |
| `SetFootprintDimensions` | `{width_m, depth_m}` |
| `SetStoryHeights` (formerly `SetLevelElevations`) | `{story_heights_m: [h0, h1]}`: sets L0 story height, L1 elevation (= h0), and L1 story height |
| `SetGableRoofParameters` | `{pitch_rad, eave_overhang_m}` |
| `SetMemberSection` | `{role, section_id}`: changes one role's section default in `FrameSystem.member_defaults` and regenerates that role; never a single member ([D040](../product/decisions/D040-setmembersection-role-default.md)) |
| `SetTimberGrid` | `{x_lines: [GridLineArg], y_lines: [GridLineArg]}`: replaces both axes' lines (§2.1) |
| `AddSection` | `{nominal_label, actual_width_m, actual_depth_m}`: adds a rectangular `Section` to the project catalog ([D038](../product/decisions/D038-field-presence-catalog-records.md)). Its ID is minted with creation key `"section"` ([D041](../product/decisions/D041-deterministic-id-minting.md)). It changes no members; use `SetMemberSection` to apply it. Dimensions must be greater than zero (stage 3). The label must be unique within the project; a duplicate is `DUPLICATE_SECTION_LABEL` with `args.nominal_label` in `related_paths` ([D049](../product/decisions/D049-unique-section-labels.md)) |
| `UndoToRevision` | `{target_revision_id}`: a new revision whose content equals the target revision's, with the current head as parent; restores original IDs; redo targets a later revision ([D044](../product/decisions/D044-undo-to-revision.md)) |

Commands use full typed arguments, not generic JSON patch paths. The envelopes' JSON Schema is exported to [`schemas/commands.v1.schema.json`](schemas/commands.v1.schema.json) (D028).

### 2.1 `SetTimberGrid` arguments

The command sends the complete list of lines for both axes ([D042](../product/decisions/D042-stable-grid-line-ids.md); approved from [MODEL-003](../implementation/tasks/MODEL-003.md) §10, item 2). Each `GridLineArg` is one of two forms:

- `{"id": "x2", "fraction": 0.5}` keeps existing line `x2` (it may move);
- `{"fraction": 0.5}` adds a new line.

Rules:

- **Removal:** base lines that are not listed are removed.
- **Order:** entries must be strictly ascending by `fraction`. They are validated, not re-sorted (D030).
- **New line IDs:** new lines are numbered in argument order. On each axis, numbering starts at one more than the largest number among the base grid's lines and the listed existing lines (D042).
- **Errors:**
  - an `id` that is not a base line on that axis is `DANGLING_REFERENCE` at `args.x_lines[k].id`;
  - an `id` listed twice is `DUPLICATE_LINE_ID`;
  - endpoints (0 and 1), station counts, and bay lengths are checked on the candidate snapshot (D032, D035).

## 3. Preview contract

`POST /api/v1/projects/{project_id}/commands/preview`

Request: command envelope. Response (illustrative; result contract approved from [MODEL-003](../implementation/tasks/MODEL-003.md) §10, item 5):

```json
{
  "preview_token": "<opaque signed string, D047>",
  "base_revision_id": "ab4c88f3-f5e9-47dd-8ee0-4c7a19a0b6cf",
  "revision_id": "<minted per D041; the revision the commit will create>",
  "command_hash": "sha256:...",
  "classification": "consequential",
  "classification_version": "vs01-change-classes-1",
  "confirmation_required": true,
  "is_noop": false,
  "changes": [
    {"entity_kind": "Footprint", "entity_id": "9ba359f1-6354-5019-9b3f-d15f8e53523b", "field": "width_m", "before": 10.9728, "after": 12.192}
  ],
  "members": {
    "added": [],
    "removed": [],
    "updated": ["2354313a-7ce0-556f-afd4-e80ebe664ef9", "..."]
  },
  "impacted_artifacts": ["mesh3d", "plan2d", "preliminary_estimate", "timber_schedule"],
  "warnings": [
    {"code": "PRELIMINARY_UNVERIFIED", "message": "Framing and estimates are preliminary. Structural adequacy has not been assessed."}
  ],
  "expires_at": "2026-11-14T18:00:00Z"
}
```

- **`changes`** lists field-level changes to records other than timber members, as `{entity_kind, entity_id, field, before, after}`.
  - `field` uses [D036](../product/decisions/D036-error-path-syntax.md) path syntax, relative to the record.
  - `before` and `after` are whole JSON values; for example, the full `x_lines` array.
  - Records added or removed by a command appear with `before` or `after` set to `null` and `field` set to `""`.
  - Entries are sorted by `(entity_kind, entity_id, field)`.
- **`members`** lists timber members:
  - `added` and `removed` are `{id, generation_key}` entries sorted by `generation_key`;
  - `updated` lists IDs of members whose geometry, section, or material changed, sorted by ID.
  - Added IDs are exactly the IDs the commit will create ([D041](../product/decisions/D041-deterministic-id-minting.md)).
- **`impacted_artifacts`** lists all four VS-01 artifact types, in lexicographic order, for every committing command. Each artifact's fingerprint covers the whole canonical snapshot ([artifacts.md](artifacts.md) §2.3), so any change makes all four stale. Narrower lists wait on per-artifact input selectors.
- **`is_noop`** is `true` when the candidate's `building` and `entities` equal the base's (canonical comparison). In that case `changes` and the `members` lists are empty, `revision_id` is `null`, and committing creates no revision ([D045](../product/decisions/D045-no-op-commits.md)).
- **`warnings`** are `{code, message}` objects and always include `PRELIMINARY_UNVERIFIED`.
- **`classification`** comes from the versioned table in [dependencies.md §4.1](dependencies.md#41-vs-01-classification-table-vs01-change-classes-1), and `classification_version` names that table.
- **`confirmation_required`** is `true` exactly when `classification` is `consequential` ([dependencies.md](dependencies.md) §4) and `is_noop` is `false`.

The preview does not modify project head or create a revision. `command_hash` is SHA-256 over the RFC 8785 canonical serialization ([D029](../product/decisions/D029-canonical-json-rfc8785.md)) of the command envelope, which includes the base revision. `preview_token` and `expires_at` are server-issued, not client-chosen. The token is an HMAC-SHA-256 signature over the canonical `{project_id, actor_id, base_revision_id, command_hash, expires_at}`, valid for 15 minutes, and nothing is stored when it is issued ([D047](../product/decisions/D047-stateless-preview-tokens.md)).

## 4. Commit contract

`POST /api/v1/projects/{project_id}/commands/commit`

Body: `{ "command": <command envelope>, "preview_token": "..." }`. The token is required for consequential commands that are not no-ops; routine commands and no-ops may omit it ([D047](../product/decisions/D047-stateless-preview-tokens.md), [dependencies.md §4.1](dependencies.md#41-vs-01-classification-table-vs01-change-classes-1)). Errors: a missing token where one is required is `PREVIEW_REQUIRED` (428); a token that does not verify or does not match the commit's project, actor, base revision, or `command_hash` is `PREVIEW_INVALID` (409); an expired token is `PREVIEW_EXPIRED` (409). Server revalidates all preconditions and commits atomically.

Commit runs in one transaction ([MODEL-004](../implementation/tasks/MODEL-004.md) §4.3, approved as §10 item 1):

1. Lock the project.
2. Check idempotency.
3. Check that `base_revision_id` is the head (`REVISION_CONFLICT` otherwise).
4. Re-run the command, which deterministically yields the preview's IDs and diff.
5. Check the preview requirement: a consequential command needs a preview; a routine command or a no-op does not.
6. Persist the revision and operation, and advance the head.

Responses:

- **New revision:** HTTP 201 with `{ "revision_id", "parent_revision_id", "operation_id", "sequence", "is_noop": false, "artifact_statuses" }`. `sequence` numbers revisions within the project from 1. Until the artifact tasks exist, `artifact_statuses` reports every VS-01 artifact type as `MISSING` (never computed, [artifacts.md](artifacts.md) §2.1).
- **Idempotent retry** (same `command_id` and `command_hash`): HTTP **200** with the original result body plus `"replayed": true`; nothing is written.
- **Creation:** `POST /api/v1/projects` follows the same rules: 201 when created, 200 on retry.
- A successful commit does **not** imply all derived artifacts are ready.

A no-op commit creates no revision: it returns HTTP 200 with `revision_id` equal to the current head, `is_noop: true`, and unchanged artifact statuses. The operation log still records the attempt ([D045](../product/decisions/D045-no-op-commits.md)).

## 5. Routes

All routes are under `/api/v1` and require authentication ([API-001](../implementation/tasks/API-001.md) §4, approved as §11 item 2). A path that matches no route returns 404 `NOT_FOUND` before authentication; this reveals only the route table, which the OpenAPI document already publishes, never whether a project exists (API-001 §13, item 3):

| Method and path | Purpose | Success |
|---|---|---|
| `POST /api/v1/projects` | Create reference project (creation envelope, §2) | 201; 200 for an idempotent retry (`"replayed": true`) |
| `GET /api/v1/projects` | The caller's own projects, newest first: `{projects: [{project_id, head_revision_id, head_sequence, created_at}]}` ([UI-001](../implementation/tasks/UI-001.md) §8.1, approved as §11 item 8) | 200 |
| `GET /api/v1/projects/{id}` | Metadata, head revision, and the caller's `permissions` (`["read", "write"]` for the owner in VS-01) | 200 |
| `POST /api/v1/projects/{id}/commands/preview` | Preview a command (§3) | 200 |
| `POST /api/v1/projects/{id}/commands/commit` | Commit `{command, preview_token?}` (§4) | 201 new revision; 200 no-op or retry |
| `GET /api/v1/projects/{id}/revisions` | Ordered revision history | 200 `{revisions: [...]}` |
| `GET /api/v1/projects/{id}/revisions/{rev}` | Immutable semantic snapshot | 200 |
| `GET /api/v1/projects/{id}/artifacts?revision_id=...` | Artifact status manifest (head when omitted) | 200 |
| `GET /api/v1/projects/{id}/artifacts/{type}?revision_id=...` | Derived 2D, 3D, schedule, or estimate | see below |
| `PUT /api/v1/projects/{id}/price-book` | Set a new price-book version ([artifacts.md §8.2](artifacts.md#82-price-book)) | 201 `{price_book_id, version, set_at}` |
| `GET /api/v1/projects/{id}/price-book` | Current price book | 200 `{price_book: {...} \| null}` |

The OpenAPI document is served at `/openapi.json`, outside `/api/v1`, and committed as [`schemas/openapi.v1.json`](schemas/openapi.v1.json). `GET …/revisions/{rev}` returns the snapshot's canonical bytes (D029, D030).

Artifact envelopes and payloads are specified in [artifacts.md](artifacts.md) (D027). `{type}` is one of `plan2d`, `mesh3d`, `timber_schedule`, `preliminary_estimate`.

**Artifact statuses:**
- `CURRENT`, `UNAVAILABLE`, and `FAILED` return 200 with the envelope. `FAILED` carries `error`.
- `MISSING` returns 202 without payload. In VS-01 this happens only for a type with no registered derivation, because reading an artifact derives it when missing or stale.
- An unknown type or revision returns 404.
- VS-01 never returns 503, because it has no external dependency that can be unavailable.

Stale data is never served as current. Browser 2D/3D views must consume derived data tagged to the same revision.

## 6. Typed module-level interfaces (Python-like pseudocode)

```python
class ModelService(Protocol):
    def validate(self, snapshot: BuildingSnapshot) -> ValidationResult: ...
    def propose(self, snapshot: BuildingSnapshot, command: ModelCommand) -> CandidateChange: ...

class GeneratedMember(Protocol):
    generation_key: str
    member_role: str
    start_m: tuple[float, float, float]
    end_m: tuple[float, float, float]
    section_id: UUID
    material_id: UUID

class TimberGenerator(Protocol):
    # Defined only for snapshots passing validation stages 1-4. Returns members without IDs,
    # sorted by generation_key (code-unit order). MODEL-003 assigns IDs: it reuses the base's
    # ID for a surviving key and mints new IDs per D041. (TIMBER-001 §10, item 1.)
    def generate(self, snapshot: BuildingSnapshot) -> tuple[GeneratedMember, ...]: ...

class DependencyService(Protocol):
    def impacts(self, changed_keys: set[str]) -> ImpactReport: ...
    def invalidate(self, revision_id: UUID, impacted: ImpactReport) -> None: ...

class GeometryAdapter(Protocol):
    def derive_plan(self, snapshot: BuildingSnapshot) -> Artifact: ...
    def derive_mesh(self, snapshot: BuildingSnapshot) -> Artifact: ...

class ScheduleService(Protocol):
    def timber_schedule(self, inventory: MemberInventory) -> Artifact: ...
```

Interfaces are illustrative. Schema definition is confirmed by [D028](../product/decisions/D028-pydantic-authoritative-schema.md): Pydantic models are authoritative, JSON Schema for the snapshot is exported and committed, and the OpenAPI generated from the same models produces the TypeScript clients. Cross-record and domain validation runs only on the server; the frontend does not duplicate it.

## 7. Error contract

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "Footprint width must be greater than zero",
    "details": [{"path":"args.width_m", "code":"OUT_OF_RANGE", "value":-1}],
    "request_id": "..."
  }
}
```

Stable codes: `VALIDATION_FAILED` (422), `UNSUPPORTED_CONFIGURATION` (422), `UNAUTHORIZED` (401), `FORBIDDEN` (403), `NOT_FOUND` (404), `METHOD_NOT_ALLOWED` (405, a known path with an unsupported method; the response carries `Allow`; API-001 §13, item 1), `REVISION_CONFLICT` (409), `IDEMPOTENCY_CONFLICT` (409), `PREVIEW_EXPIRED` (409), `PREVIEW_INVALID` (409), `PREVIEW_REQUIRED` (428) ([D047](../product/decisions/D047-stateless-preview-tokens.md)), `DERIVATION_FAILED` (500/503 as appropriate), `INTERNAL` (500, any unexpected server error). No internal stack traces in API responses.

**HTTP request handling** ([API-001](../implementation/tasks/API-001.md) §5, approved as §11 item 3):

- **Strict bodies:** JSON request bodies are parsed with the same strict parser as snapshots (MODEL-001 §5.1), not a framework default. Duplicate keys, `NaN`/`Infinity`, and oversized or overly deep bodies return 422 `VALIDATION_FAILED`, with `MALFORMED_JSON`, `DUPLICATE_KEY`, `NON_FINITE_NUMBER`, or `PAYLOAD_LIMIT_EXCEEDED`. A body that is not `application/json` returns 415 with top-level `VALIDATION_FAILED` and one detail `{path: "", code: "MALFORMED_JSON"}` (API-001 §13, item 2).
- **Request IDs:** every response carries `X-Request-ID`. It is generated by the server and never taken from the client, and error bodies repeat it as `request_id`.
- **Unexpected errors:** an unexpected error, including a stored revision whose fingerprint no longer matches, returns 500 `INTERNAL` without internals. It is logged with its request ID and no project content.

Detail `code` values for model validation are cataloged in [building-model.md §6.1](building-model.md#61-detail-codes); each belongs to one validation stage, which determines whether the top-level code is `VALIDATION_FAILED` or `UNSUPPORTED_CONFIGURATION` ([D035](../product/decisions/D035-validation-stages-detail-codes.md)).

Detail `path` syntax ([D036](../product/decisions/D036-error-path-syntax.md)): paths start at the root of the validated document (`""` is the whole document). Fields are joined with `.` (`args.width_m`, `building.footprint_id`), and keys that are not identifiers use `["…"]`. Snapshot entities are addressed by ID (`entities[<id>].width_m`), or by position (`entities[#12]`) when the ID is missing, malformed, or duplicated. Other arrays use zero-based indexes (`x_lines[2].fraction`).

A detail may include an optional `related_paths` array listing other fields that contribute to the issue, such as the footprint width behind a bay-length violation. Entries are unique, sorted, and never repeat `path`, and the array is left out when empty ([D037](../product/decisions/D037-error-related-paths.md)). Each detail is `{"path", "code", "value"?, "related_paths"?}`; `message` text on the envelope is human-readable and not part of the contract.

### 7.1 Command errors

Approved from [MODEL-003](../implementation/tasks/MODEL-003.md) §10, item 8. These rules apply to preview and commit.

| Situation | Top-level code | Detail paths |
|---|---|---|
| `base_revision_id` differs from the base snapshot's revision | `REVISION_CONFLICT` (409) | Checked first; nothing is computed; no detail issues |
| `project_id` differs from the base snapshot's project | `VALIDATION_FAILED` | `project_id`, detail code `DANGLING_REFERENCE` |
| Malformed envelope or arguments: unknown `type`, missing, unknown, or wrong-type argument | `VALIDATION_FAILED` (stage 1) | Envelope paths: `type`, `args.width_m`, `args.x_lines[2].fraction`. Processing stops |
| Argument references a missing or wrong-kind item: line ID, section, target revision | `VALIDATION_FAILED` (stage 2) | `args.…` paths (for example `args.section_id`, `args.x_lines[1].id`) |
| The candidate snapshot fails validation | Code of the first failing stage ([D035](../product/decisions/D035-validation-stages-detail-codes.md)) | Snapshot paths. When a failing field (`path` or any `related_paths` entry) was set directly by an argument, that argument's path is added to `related_paths` ([D037](../product/decisions/D037-error-related-paths.md)) |

- **Argument-to-field mapping:** each command defines which snapshot fields each argument sets, for example `args.width_m` → `Footprint.width_m`. A bay-length error after `SetFootprintDimensions {width_m: 23}` therefore has `path` = the grid's `x_lines`, and `related_paths` = [the footprint's `width_m`, `args.width_m`], so a UI can highlight the input the user just changed.
- **Codes:** command errors use the existing catalog (building-model.md §6.1) plus the top-level codes above. No command-specific detail codes exist in VS-01.

## 8. Concurrency, security, and compatibility

- Every read/write is project-scoped and authorization-checked on server. In VS-01 ([D050](../product/decisions/D050-vs01-authentication-authorization.md)):
  - **Authentication:** a pluggable authenticator; the development authenticator maps configured bearer tokens to actor UUIDs, and a missing or unknown token is 401 `UNAUTHORIZED`.
  - **Authorization:** only a project's creator may read or write it. Any other actor receives 404 `NOT_FOUND`, the same as a nonexistent project.
- Use optimistic concurrency on project head (D026). In VS-01, artifacts are derived synchronously after commit and recomputed on read, so there is no outbox or job queue ([dependencies.md §6](dependencies.md#6-incremental-recomputation), ART-001).
- Never accept arbitrary executable expressions, geometry scripts, or SQL from AI/client as commands.
- API version prefix `/api/v1`; model schema versions independent of API version.
- Schema changes require backward-compatible readers or explicit migrations, contract tests, and fixture upgrades.
- An audit record is appended for **every commit attempt**: actor, command, `command_hash`, base revision, result (`committed`, `noop`, or `rejected`), top-level error code if rejected, new revision if any, classification and its version, and timestamp. Audit rows are never updated or deleted. Routine logs carry no snapshot content ([MODEL-004](../implementation/tasks/MODEL-004.md) §4.5).

## 9. Contract test matrix

1. OpenAPI validates example requests/responses; generated TS client compiles. The OpenAPI document is generated from the Pydantic models and committed as [`schemas/openapi.v1.json`](schemas/openapi.v1.json), with a drift check (API-001). Generating and compiling the TypeScript client is part of `UI-001`.
2. Valid preview has no database side effects.
3. Confirmed commit changes project head exactly once.
4. Two concurrent commits against one base revision yield exactly one winner; loser receives 409.
5. Idempotent retry does not duplicate revisions or derivation jobs.
6. Unauthorized project access cannot read snapshots or artifacts.
7. Derived plan, mesh, and schedule all identify matching source revision.
8. Unsupported geometry returns structured error, never an unhandled exception or invented output.

## 10. Deferred contracts

Professional approval signatures, alternative branches/merges, IFC export, engineering load cases, natural-language proposals, multi-user live editing, and detailed connection machining are not VS-01 endpoints. Add them via separate versioned design documents.
